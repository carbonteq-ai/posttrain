# Make GRPO runs research-readable across TRL and veRL

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This plan follows `docs/templates/PLAN.md`; the planning skill's usual `.agents/PLAN.md` entrypoint is not present in this repository.

## Purpose / Big Picture

After this work, an AI researcher can open a `train.grpo` run in Observatory and answer five questions without knowing whether TRL or veRL executed the job: did the verifier produce a usable learning signal, did the policy actually update, did the update remain controlled, were the rollouts valid and generated by the intended policy version, and did MTP or TurboQuant improve execution enough to justify its cost or risk.

The GRPO page will not be a generic collection of native trainer metrics. It will present a stable core view for every GRPO run, a rollout-and-reward population backed by native Verifiers traces, and conditional acceleration evidence when the selected inference binding enables multi-token prediction (MTP) or a TurboQuant KV cache. “Conditional” means required when the feature is selected, not optional evidence that an adapter may silently omit.

A developer can see the result by running matched short GRPO jobs through TRL and veRL, logging one through Trackio and one through W&B, selecting either source in Observatory, and comparing the normalized views. The same logical fields, chart questions, alerts, and MCP payloads must appear for both training backends. Provider-native metric names remain available only in the native training summary artifact and generic metric inspection; they do not define the product view.

This work began as an implementation of the frozen observation baseline. On 2026-07-23 it also made one narrow product amendment: `train.grpo` is environment-only. A GRPO work package binds one versioned Verifiers environment reference with category and bounded-sampling policy; it does not bind a dataset or exact task-id selection. The trainer-facing rollout dataset remains an internal bridge projection, while concrete resolved task identities remain replay evidence in Verifiers traces. The amendment is recorded in `docs/post-training/README.md`, `02-primitives.md`, and `05-apis.md` before the corresponding lab refactor.

## Surprises & Discoveries

- Observation: the current Observatory GRPO definition is much thinner than the SFT and DPO definitions.
  Evidence: `apps/observatory/src/posttrain_observatory/telemetry.py` currently registers only reward mean, reward standard deviation, KL, entropy, and clip fraction for `train.grpo`; it has no evidence requirements and no rollout, optimizer, performance, MTP, or TurboQuant contract.

- Observation: TRL already computes most of the required normalized evidence, but the generic callback currently prefixes native names instead of translating their meaning.
  Evidence: the pinned CarbonTeq TRL fork logs `reward`, `reward_std`, `frac_reward_zero_std`, `policy_loss`, `kl`, `entropy`, clip ratios, completion lengths, tool frequencies, sampling-log-probability deltas, and importance-sampling ratios. `packages/train/src/posttrain/train/backends/trl/common.py` currently turns those into names such as `train/reward` and `train/rollout/spec_accept_rate` without a GRPO-specific mapping.

- Observation: the TRL MTP implementation converts vLLM process-lifetime speculative counters into one-generation deltas, but one isolated distillation test had not initialized the newly added `last_generation_metrics` collaborator state.
  Evidence: `/home/hammad/projects/trl/trl/generation/vllm_generation.py` computes draft tokens, accepted tokens, acceptance rate, and accepted length, and `/home/hammad/projects/trl/trl/trainer/grpo_trainer.py` adds them to trainer logs. Initial focused validation produced one `MagicMock`-driven failure; initializing the state in that test restored the intended isolated contract. The reviewed change and test fix are committed and pushed as `08775d163b8c89d289839ad7725548a6e7ef5d23`.

- Observation: equivalent logical GRPO evidence can be normalized without importing either trainer or either tracking provider.
  Evidence: `packages/train/tests/fixtures/grpo_metrics/trl_step.json` and `verl_step.json` now produce identical 30-field canonical mappings. Async, MTP, TurboQuant, and malformed partial-evidence fixtures exercise conditional obligations independently.

- Observation: veRL already has a structured local file logger, so the workspace adapter does not need to scrape printed Python dictionaries or make veRL talk directly to Trackio or W&B.
  Evidence: `/home/hammad/projects/verl/verl/utils/tracking.py` supports `trainer.logger=file` and writes `{"step": ..., "data": ...}` JSONL to `VERL_FILE_LOGGER_PATH`. The native trainer records reward, advantage, response-length, actor loss, gradient norm, KL, entropy, clip fraction, phase timing, throughput, memory, and speculative acceptance metrics.

- Observation: MTP acceptance is not itself evidence of a speedup.
  Evidence: the recent Qwen 3.5 MTP probe measured high acceptance but also roughly 501 MiB additional GPU memory at a matched rollout budget. The page must place acceptance beside rollout tokens per second, rollout time, step time, and peak memory.

- Observation: TurboQuant capacity can improve while correctness regresses.
  Evidence: the recent K8V4 probe increased cache capacity from 291,328 to 776,722 tokens but failed matched recall at 8K through 32.7K, while normal FP16 KV passed. A GRPO dashboard must never label a quantized KV cache “better” from capacity or throughput alone.

- Observation: the current veRL adapter returns only a final summary to the host even though the native runtime produced rich step metrics.
  Evidence: `packages/train/src/posttrain/train/backends/verl/worker.py` uses regular expressions to recover the last native values and writes only global step, final loss, runtime, samples per second, and steps per second to `posttrain-result.json`.

- Observation: the current veRL fork does not yet emit a complete MTP counter set.
  Evidence: its aggregator exposes `rollout/spec_accept_rate` and `rollout/spec_accept_length`, but not the raw drafted-token and accepted-token totals required to prove the denominator. The shared normalizer therefore rejects this partial record instead of manufacturing counts.

- Observation: neither qualified runtime currently emits structured TurboQuant KV-cache capacity and peak-use counters into the GRPO step stream.
  Evidence: the selected `kv_cache_dtype` is available as resolved configuration, but no runtime-owned capacity or peak-use observations exist. Observatory now marks the conditional evidence missing when TurboQuant is selected instead of equating selection with qualification.

- Observation: reducing the actor batch to one did not bound the large-vocabulary
  scoring allocation.
  Evidence: the matched AutomationBench attempts first requested another 1.43
  GiB during full-batch scoring and then attempted a 3.54 GiB logits tensor
  with physical batch one. Chunking token positions through the frozen LM head
  and using a fused differentiable loss crossed that boundary.

- Observation: feature-inactive acceleration surfaces were misleading even when technically marked missing.
  Evidence: the first fixture browser audit showed “MTP off” beside a missing MTP-acceptance KPI and an entirely empty acceleration tab. Whole charts with no observed series are now omitted, while selected features still receive explicit incomplete-evidence cards.

- Observation: TRL's native `loss` field is the GRPO policy objective in current trainer logs even when `policy_loss` is not present.
  Evidence: the real one-step TRL run emitted `loss`; mapping it to `train/rl/policy_loss` closed the controlled-update obligation without changing SFT or DPO callback behavior.

- Observation: W&B's long-lived Public API object caches the project run collection.
  Evidence: a fresh reader listed seven runs while the already-running Observatory process listed five. Calling the supported API refresh before `list_runs` made the two readers converge and is covered by the adapter unit test.

- Observation: provider selection exposed a frontend evidence-integrity race even though both readers returned correct data.
  Evidence: the header switched to the failed W&B run while the page retained the successful Trackio run's completeness, charts, traces, and artifacts. Keying loaded state by `run_key`, clearing it on selection, and rejecting late responses removed the cross-run mixture; an in-app browser check now sees an empty loading projection during each switch.

- Observation: the constrained 0.8B topology fits the 8 GB GPU in TRL but does not establish veRL compatibility.
  Evidence: the TRL MTP+LoRA run completed with exact counters, while the matched veRL MTP+LoRA run exited during vLLM async engine initialization. Earlier 2B attempts exhausted memory; the 0.8B failure therefore remains a backend/runtime blocker rather than evidence that the original 2B topology fits.

- Observation: an async protocol does not make a synchronous provider SDK non-blocking.
  Evidence: W&B reader methods were declared `async` but SDK initialization, GraphQL scans, history reads, and artifact downloads executed synchronously. Thread offload still allowed SDK initialization to monopolize the GIL inside the container. A spawned single-worker process keeps one cached W&B API session while isolating its GIL and network work from Observatory's HTTP/MCP event loop.

- Observation: source readiness is the wrong Docker liveness probe for a multi-provider read product.
  Evidence: `/health/ready` deliberately probes every configured source and can wait on W&B convergence, so a two-second Docker timeout marked a responsive server unhealthy. `/health/live` directly tests the serving process; source health remains visible through the readiness and source APIs.

- Observation: the original veRL failure used a stale local runtime, while the previously qualified checkout used a newer vLLM/Transformers/Torch environment and stricter memory settings.
  Evidence: the failed attempt used `/home/hammad/projects/verl/.venv` with vLLM 0.18.0; the recovered path uses `/home/hammad/projects/verl-upstream/runtime/turboquant-cu130/.venv` with vLLM 0.25.1, 0.55 rollout GPU utilization, sleep/offload, fused output projection, and chunked entropy.

- Observation: a source checkout plus Python interpreter is not a reproducible isolated veRL selection when the runtime lock omits environment packages used by Ray workers.
  Evidence: the first retry could start vLLM but produced an empty rollout batch because the isolated environment did not own the pinned GSM8K/Verifiers packages. The completed runtime lock now pins veRL, Verifiers, `gsm8k-v1`, and Automation Bench together and its SHA-256 is recorded in the run configuration.

- Observation: importing a submodule executes its package root before Ray unpickles the agent loop.
  Evidence: `posttrain_lab.__init__` eagerly imported `execution`, which imported `posttrain.tracking`; that package was intentionally absent from the isolated runtime. A lazy public export keeps `posttrain_lab.environments.gsm8k_grpo` independently importable and is covered by a subprocess import test.

- Observation: a successful GPU step can still fail during artifact production when the run workspace lives on the desktop session's small tmpfs.
  Evidence: retry `8803f729-fb15-41e1-8ace-ce1cb6109e38` finished training and reached model merge, then raised `No space left on device`. Moving unique run workspaces under the explicit disk-backed scratch root allowed model merge, adapter export, and the recovery checkpoint to complete.

- Observation: durable recovery checkpoints materially extend W&B finalization time even for a one-step qualification.
  Evidence: the adapter and summary are small, but the veRL FSDP recovery checkpoint is approximately 3.4 GiB. W&B keeps `finish()` synchronous until that artifact is uploaded, so logical completion can precede provider terminal-state convergence by many minutes.

- Observation: equal resolved GRPO settings do not guarantee equal realized rollout work, and the first normalized throughput mapping hid a numerator mismatch.
  Evidence: TRL stopped after 6 completion tokens per rollout while veRL averaged 293 tokens and truncated one rollout. TRL's rollout rate divided completion tokens by generation time, but veRL's fallback divided `perf/total_num_tokens` (prompt plus completion training tokens) by generation time. veRL now emits exact response-token totals and the normalizer uses those totals for rollout throughput.

  Evidence: `apps/lab/src/posttrain_lab/work_packages/definitions.py` declared a dataset seat of type `GSM8KTaskSelection`, and `run_grpo_materialized` rebuilt a GSM8K bridge from exact row indices. That hard-coded composition is why the earlier matched benchmark exercised GSM8K instead of Zapier AutomationBench.

  Evidence: `environments/automationbench_v1` pins CarbonTeq AutomationBench 1.0.5 at `d54dbebabdba6c6eda201694aee8ddcf36ccfc51`, implements `AutomationBenchTaskset`, Zapier toolsets, native reward/metrics, and passes its six port tests. The lab bridge imports that taskset in the Python 3.12 trainer runtime and retains its native traces.

  Evidence: unpacking the exact cached wheel at `a321764ace3cfbe42289e6a13abef2f0f4f56fad` onto the Python 3.12 import path made all six port tests pass, while normal `uv pip install --dry-run` rejected the same revision only because `automation-bench==1.0.5` declares `Python>=3.13`.

## Decision Log

- Decision: make GRPO environment-only and keep datasets as SFT/DPO inputs in the current product surface.
  Rationale: Verifiers environments already own task populations, tools, interaction, and scoring. A second dataset/task seat gives the host two competing authorities for the rollout population and leaks the trainer bridge into work-package composition.
  Date/Author: 2026-07-23 / Codex.

- Decision: select Zapier AutomationBench through environment domains/categories and bounded deterministic sampling, not exact task IDs.
  Rationale: environment-internal row numbers are a brittle authoring surface. Domain filters, a sampling seed, task budget, rollout budget, and GRPO step budget express researcher intent; resolved task identities belong in Verifiers traces and the resolved-run evidence needed for replay.
  Date/Author: 2026-07-23 / Codex.

- Decision: do not weaken dependency provenance to bypass AutomationBench's Python metadata.
  Rationale: a manually patched wheel would make the run depend on state that is absent from the catalog, lockfile, and artifact lineage. The acceptable production paths are an immutable compatibility fork after the passing Python 3.12 suite, or an explicit isolated rollout-worker protocol. The former is narrower; the latter is necessary only if upstream begins using real Python 3.13 behavior.
  Date/Author: 2026-07-23 / Codex.

- Decision: maintain the narrow Python 3.12 compatibility delta in `carbonteq-ai/AutomationBench`.
  Rationale: the fork makes the package contract truthful and lockable while leaving benchmark behavior, datasets, tools, and scoring under upstream ownership. The root repository records only an immutable fork SHA; any later behavioral patch needs its own compatibility and scoring evidence before the pin moves.
  Date/Author: 2026-07-23 / Codex.

- Decision: organize the GRPO view around researcher questions rather than backend metric names.
  Rationale: reward, update stability, rollout integrity, policy freshness, and execution efficiency are stable concepts across TRL and veRL; `actor/pg_loss`, `policy_loss`, and other native spellings are not.
  Date/Author: 2026-07-22 / Codex.

- Decision: define a mandatory core and conditionally mandatory feature evidence; reserve “diagnostic” for values that do not determine run completeness.
  Rationale: every GRPO backend must prove that it generated a usable reward signal and performed a controlled update. MTP, TurboQuant, reference-KL, and decoupled rollout evidence only apply when selected, but become required in that case. Missing applicable evidence is a visible incomplete-evidence state, not a blank chart.
  Date/Author: 2026-07-22 / Codex.

- Decision: normalize metrics inside `packages/train`, before tracking, rather than translating TRL and veRL names in Observatory.
  Rationale: Trackio, W&B, Python callers, MCP, and the frontend must receive the same logical evidence. If Observatory owns native-name translation, every other reader would diverge and the tracking boundary would leak training backends.
  Date/Author: 2026-07-22 / Codex.

- Decision: keep Verifiers traces as the per-rollout authority and metrics as bounded step or run aggregates.
  Rationale: transcripts, reward components, tool calls, truncation, environment turns, and exact example identities are high-cardinality evidence. Duplicating every rollout into scalar metrics would lose replayability and inflate tracking stores.
  Date/Author: 2026-07-22 / Codex.

- Decision: use `serve/backend/*` for rollout-engine MTP and KV-cache counters and `train/rl/*` for GRPO learning and population aggregates.
  Rationale: the canonical baseline already assigns engine, scheduler, cache, and speculative counters to `serve/backend/*`, even when the engine is embedded in a training run. Reusing that namespace makes the same vLLM evidence comparable in benchmark and GRPO contexts.
  Date/Author: 2026-07-22 / Codex.

- Decision: preserve backend-native structured logs as an artifact, but do not expose them as the curated contract.
  Rationale: native logs are valuable for deep diagnosis and future mappings. Keeping them separate prevents the curated page from becoming a union of every TRL and veRL metric.
  Date/Author: 2026-07-22 / Codex.

- Decision: label the GRPO trace area “Rollouts & rewards” while retaining the existing trace API and top-level route.
  Rationale: SFT and DPO correctly hide trace/evaluation, but GRPO rollouts are part of the training evidence, not a separate offline evaluation. A job-specific label makes the purpose clear without changing trace ownership.
  Date/Author: 2026-07-22 / Codex.

- Decision: do not qualify TurboQuant from a GRPO reward curve.
  Rationale: stochastic reward cannot isolate cache-precision regressions. The UI may show the selected KV mode and its operational metrics, but correctness status must come from a matched qualification artifact or an explicitly comparable baseline run.
  Date/Author: 2026-07-22 / Codex.

- Decision: use veRL's existing `file` logger through the isolated runtime instead of adding a direct Trackio or W&B writer to veRL.
  Rationale: the host owns the logical run and tracking backend. The file sidecar gives the host structured native observations without credentials in Ray workers or duplicate provider runs.
  Date/Author: 2026-07-22 / Codex.

- Decision: represent applicability as a resolved `GRPOObservationFeatures` value and keep the normalizer independent of the full request after feature resolution.
  Rationale: this makes conditional obligations explicit and easy to test while keeping the pure normalization boundary free of TRL, veRL, vLLM, Trackio, and W&B objects. Missing selected-feature evidence is reported by name; unselected features do not create false gaps.
  Date/Author: 2026-07-22 / Codex.

- Decision: do not render a curated chart when none of its registered series has observations.

## Research Questions and Evidence Contract

The curated GRPO view must answer the following questions in this order.

First, “is there a usable learning signal?” The required metrics are `train/rl/reward_mean`, `train/rl/reward_std`, `train/rl/group_zero_variance_fraction`, `train/rl/rollouts_attempted`, `train/rl/rollouts_completed`, `train/rl/rollouts_failed`, `train/rl/rollouts_truncated`, and `train/rl/rollouts_unscorable`. Reward-component means remain derived from Verifiers traces and are shown when the environment exposes components. A group-zero-variance fraction of one means GRPO has no within-prompt relative signal even if the global reward standard deviation is non-zero.

Second, “did the policy actually update, and was the update controlled?” The required metrics are `train/rl/policy_loss`, `train/grad_norm`, `train/learning_rate`, and `train/step_time_seconds`. `train/rl/entropy` is also required for the qualified TRL and veRL paths because both current runtimes expose it. `train/rl/kl` and `train/rl/clip_fraction` are conditionally required when the selected objective enables reference KL or clipping. Parameter counts and the selected full, LoRA, or QLoRA update remain configuration and artifact metadata rather than step metrics.

Third, “are rollouts valid and representative?” The required aggregates are `train/rl/completion_tokens_mean`, `train/rl/completion_tokens_max`, `train/rl/completion_truncation_rate`, `train/rl/tool_call_frequency`, and `train/rl/tool_failure_frequency` when tools are present. The native Verifiers trace population remains required and supplies exact prompt group, generation, reward components, turns, model tokens, environment tokens, tool calls, latency, truncation, error, and trace identity. The service derives reward distribution, completion-length distribution, task-slice distribution, and success rate when an environment defines success.

Fourth, “were rollouts produced by the intended policy?” When rollout generation is decoupled from the actor forward pass, require `train/rl/sampling_logp_delta_mean`, `train/rl/sampling_logp_delta_max`, `train/rl/importance_sampling_ratio_mean`, `train/rl/importance_sampling_ratio_min`, and `train/rl/importance_sampling_ratio_max`. For asynchronous veRL modes, also require `train/rl/policy_staleness_mean`, `train/rl/policy_staleness_max`, and `train/rl/trajectory_version_span_mean`. For synchronous runs these values may be explicit zeros or carry a `synchronous=true` event; they must not appear as unexplained missing data.

Fifth, “did acceleration help without invalidating the run?” Every run records `train/rl/rollout_tokens_per_second` plus phase timings for rollout, reward, actor forward, actor update, weight synchronization, checkpointing, and total step. Use names under `train/rl/time/*_seconds`. System GPU utilization and memory remain queried for the run time window through the existing `system/*` reader and are not written by the training adapter.

When MTP is selected, require `serve/backend/speculative_draft_tokens`, `serve/backend/speculative_accepted_tokens`, `serve/backend/speculative_acceptance_rate`, and `serve/backend/speculative_accepted_length`. Display the configured method and speculative-token count from the inference binding. Acceptance is interpreted only beside rollout tokens per second, rollout time, total step time, and GPU memory.

When TurboQuant is selected, require `serve/backend/kv_cache_capacity_tokens` when the engine exposes it and `serve/backend/kv_cache_peak_usage_ratio` during the run. Display KV-cache dtype, rollout dtype, maximum model length, batched-token limit, and maximum sequences from the inference binding. Show a visible “qualification not attached” state unless lineage includes a matched cache-qualification artifact recording model revision, cache dtype, tested context lengths, probe digest, and pass/fail outcome. A failed qualification must produce an error alert even when training completes.

Metric points use logical optimizer step. Rollout population counters generated before an update carry the upcoming optimizer step and an attribute `phase=rollout`; post-update rollout evidence carries the resulting model version. Do not use wall-clock order as a substitute for model-version identity. High-cardinality fields remain on traces or artifacts.

## Page and Interaction Design

The run header keeps project, work package, run identity, status, backend, start time, duration, and host-sample count compact. The right evidence rail shows policy and reference model lineage, environment and dataset revisions, training and rollout bindings, algorithm settings, update plan, and produced model/checkpoint/summary artifacts. Algorithm settings include beta, prompt groups per step, generations per group, prompt and completion limits, reward scaling, clipping, and importance-sampling mode. Rollout settings include engine, precision, MTP configuration, KV-cache mode, context capacity, concurrency, and phase-sharing/sleep behavior.

The Overview page begins with a six-cell evidence strip: mean reward, usable-group rate (one minus zero-variance-group fraction), rollout completion rate, KL or policy loss, gradient norm, and rollout tokens per second. Each metric has the existing information popover. Missing required evidence uses a named state such as “not emitted by adapter” or “feature selected but counter absent,” never a dash without explanation.

Below the strip, use four compact segmented sections rather than one chart with unrelated axes. “Learning signal” plots mean reward with a variability band or adjacent standard-deviation series and usable-group rate. “Optimization” plots policy loss, KL, entropy, and clip fraction in compatible small multiples, with gradient norm and learning rate in a separate stability card. “Rollout population” summarizes completion, truncation, failure, reward distribution, length distribution, turns, and tool behavior and links directly into individual traces. “Efficiency” uses a stacked or aligned phase-time view plus rollout throughput and system memory/utilization.

The top-level trace tab is visible for GRPO and labeled “Rollouts & rewards.” It groups traces by prompt group and orders generations within the group. The default table columns are prompt/example, generation, reward, reward components, completion tokens, turns, tool calls, latency, truncation, error, and policy version. Selecting a row opens the transcript, reward decomposition, token/mask accounting, tool calls, and immutable trace metadata. Aggregate charts always link back to the filtered trace population that produced them.

The acceleration card is absent for ordinary runs. For MTP, it shows configured depth, drafted tokens, accepted tokens, acceptance rate, accepted length, rollout throughput, rollout time, and memory delta if a comparable baseline is selected. For TurboQuant, it shows cache dtype, capacity, peak use, context headroom, throughput, memory, and qualification status. If both are enabled, the card states that their effects are confounded unless a matched comparison run isolates one variable.

The Compare page permits TRL-versus-veRL and acceleration comparisons only after showing a comparability header. The header checks policy and reference revisions, environment and dataset revisions, renderer, prompt/completion limits, seed, number of prompt groups, generations, update plan, and job-definition version. Backend, MTP, and KV-cache mode may intentionally differ. Any other difference is highlighted before metrics. Comparison defaults to reward signal, update stability, rollout validity, throughput, phase time, and peak memory; it does not collapse the result into one winner score.

## Idempotence and Recovery

Metric normalization and fixture generation are pure and safe to rerun. veRL sidecar paths are created only inside a unique run workspace. The launcher validates that a returned path does not escape that workspace. If an isolated process fails, keep the manifest, native log, structured JSONL, traces, and partial checkpoint; do not replay a successful completion event. Retry with a new run id or an explicitly compatible recovery checkpoint.

Do not reset or clean the current dirty worktrees. The TRL changes belong to the existing user work and must be reviewed and committed in their own repository before the consumer pin changes. If a root pin update fails, restore only the attempted manifest and lockfile edits with an explicit patch; do not use `git reset --hard` or discard unrelated work.

The real GPU matrix uses unique output directories and run ids. Reusing a cached immutable model snapshot is safe. Trackio and W&B writes use separate logical run ids unless the backend contract supports an idempotent resume. A failed credentialed W&B run may be retried after credentials are corrected without rerunning training by replaying the preserved normalized sidecar into a new tracking run clearly labeled as a replay.
