## Purpose / Big Picture

An environment should be able to report what happened at episode, turn, or tool-call level using deterministic checks, a model, or both, then assign the resulting learning signal to the relevant actions and original token spans. Verifiers must own a reusable native credit-assignment interface, not stop at storing assessments or locating their subjects. Trainers consume explicit assigned contributions rather than guessing attribution, masks, or local weighting. Existing scalar evaluation results must remain comparable.

Deliver in this order: qualify the core API enough for safe AutomationBench calibration; collect verified Luna traces and redesign, implement, and test AutomationBench's episode/turn rewards, partial credit, and guards; use that work to repair and qualify generic API gaps; then migrate all six maintained environment packages and qualify the published dependency set. AutomationBench is the first substantive API consumer, so its reward design informs the wider migration. Freeze the accepted redesign before benchmarking Qwen3.5 9B/4B/2B, building 2B/4B curricula, and collecting the final 4B bank. All three Qwen models use only the frozen subset Luna has verifiably solved. Small API fixtures are separate from the full campaign.

Luna generates candidate reference executions for reward redesign and length/tool-call budgets. They are not teacher supervision, imitation targets, or student policy-gradient samples. The Qwen benchmarks supply each target model's own behavior for curriculum design. Stop after retaining ten fresh 4B rollouts per selected development task scored with the frozen redesign. Training and further reward changes using that bank are separate work.

The API proposal is `docs/research/verifiers-assessment-api.md`. The AutomationBench execution detail is `docs/plan/automationbench-teacher-calibration-and-action-rewards.md`, titled “Redesign AutomationBench rewards from Luna traces, then prepare Qwen curricula.” Its filename remains stable for existing links. ## Interfaces and Dependencies

The proposed Verifiers interface is `async assess(request: AssessmentRequest, context: AssessmentContext) -> AssessmentBatch`, with the existing yielded-result form sharing the same publication validator. The context supplies immutable raw evidence or working copies under the selected visibility policy and optional injected inference, without trainer or Posttrain imports. Assessor internals are unrestricted by a fixed stage protocol. Optional helpers support source selection, rendering, receipts and publication; custom workflows supply equivalent provenance. A task decorator is convenience syntax over this same protocol. Public names may be refined once before adoption; update the proposal, tests, and consumers together rather than maintaining aliases indefinitely.

`SourceSnapshot` identifies immutable source data. `SubjectRef` addresses an episode, native trace/node, call occurrence, or explicit span. `ObservationView` identifies actual observed inputs and scope. `AssessmentRun` records producer/config/attempt identity and expected coverage. `Assessment` contains subject, signal meaning, status, optional finite value, and evidence references. `AssessmentBatch` retains results, failures, and derivations. `ProjectionResult` maps subjects to original token coordinates with declared fidelity and provenance. Parent dependencies are immutable and acyclic; missing required inputs cannot yield valid derived numbers.

Training consumers choose which components are required, how values become advantages, and which supports enter policy, KL, ratio, and reduction terms. Native projection does not decide their objective. A valid assessment without a usable projection remains available to evaluation. A projection's exact coordinates do not prove that its label is correct or causally certain.

Native `CreditAssignment` records preserve accepted finding IDs, recipient references, source/rule identity, signal semantics, allocation, gates and status independently of alignment. Optional aligned support is verified against original sampled tokens and the selected branch occurrence. Evidence targets, credit recipients and consumer positions are distinct. Unsupported signal forms remain retained evidence and fail incompatible consumer admission explicitly. Episode/local signal composition must be named; missing assignment or alignment never silently becomes zero.

The external environment packages depend on one immutable Verifiers revision and their own data/scoring dependencies. Optional model inference is bound by composition, with bounded execution and real provider qualification before support claims. AutomationBench calibration preserves the native evaluation runner, tasks, MCP evidence and episode store. The signed-in account route requires a qualified Codex SDK harness adapter because the existing ACP harness forces gateway authentication. Resolve that adapter's SDK/runtime identity and observe allowance/credit usage; existing credits and subscription allowance are both authorized. No generic workflow engine, trainer framework or parallel trace store is required.
