# Release Posttrain v0.4 through immutable RCs, then clean the registry safely

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must remain current while work proceeds. It follows `docs/templates/PLAN.md`; this repository does not contain the `.agents/PLAN.md` referenced by the orchestration skill, so the checked-in template is the operative plan contract.

## Purpose / Big Picture

Posttrain v0.4 should ship the framework behavior already proven end to end without confusing development artifacts with a stable release. A maintainer will be able to publish successive immutable `0.4.0rcN` packages to the development index, qualify one exact RC and its runtime-image materialization, and then publish stable `0.4.0` from that accepted source. After stable installation and rollback are proven, infrastructure maintainers will be able to remove only OCI manifests and development packages that a digest-level reachability audit proves unreferenced.

## Surprises & Discoveries

- Observation: The repository already had RC allocation and staged-version support, but the protected candidate workflow bypassed it and published final-version packages to development.
  Evidence: `apps/release/src/posttrain_release/candidate.py` allocates `X.Y.ZrcN`, while the previous `.github/workflows/release-candidate.yml` explicitly omitted that command.
- Observation: The legacy development index already contains `posttrain-0.4.0-py3-none-any.whl` and `posttrain-0.4.0.tar.gz` from an older accepted candidate, but stable has not yet released v0.4.
  Evidence: the development PEP 503 page exposes those filenames; GitHub run `34340433050` identifies source `2ffe235e45843c2e9b3e330342dc03913713056f`.
- Observation: The prior final workflow treated candidate ancestry as sufficient even when later commits could alter package inputs.
  Evidence: its ancestor branch skipped the file-level unsafe-change check. The revised workflow compares trees and applies the allowlist whenever they differ.
- Observation: runtime images should retain the authored final release identity while Python development packages use RC versions.
  Evidence: OCI image identity is an immutable digest selected by `published.toml`; rebuilding heavy CUDA layers for each RC number would add cost without changing runtime content.
- Observation: deterministic source readiness is green, but it does not turn candidate experiments into stable capability claims.
  Evidence: `/tmp/posttrain-v0.4-readiness.json` records all six source checks successful while the Lab registry intentionally retains 48 experiments as `candidate` and 20 maintained gates as `active`.
- Observation: manually dispatched Quality was strict about a stale generated runtime-image manifest and could not represent the documented pre-candidate lock exception.
  Evidence: Quality run `34584242603` rejected the changed `eval.lock.txt` because its published image still records the prior digest. The workflow now exposes an explicit default-off `allow_pending_runtime_lock` input; ordinary push/main quality remains strict.
- Observation: the base Quality environment exposed one async-runtime test that implicitly depended on the optional Verifiers extra.
  Evidence: Quality run `34584460086` passed all package imports and the dedicated Verifiers bridge job, but the base test process failed importing `verifiers.v1`. The test now skips when the optional extra is absent and is explicitly exercised in the optional-Verifiers job.
- Observation: RC1 did not fail from GPU memory pressure or NCCL.
  Evidence: the retained worker and release-runner logs show training reached finalization, Trackio returned HTTP 502 while acknowledging multipart part 24, and the provider terminated the job only after tracking remained inconsistent; exit 137 was a consequence of termination.
- Observation: root runtime-lock materialization did not refresh the transform environment.
  Evidence: `transform.lock.txt` is derived from `tools/quantization/uv.lock`, while `posttrain-release lock-runtime-dependencies` intentionally exports only root-workspace closures. RC1 therefore retained Trackio dev21 in the transform lock after the root pin changed.
- Observation: RC2 produced and retained the required model but still reported failure.
  Evidence: `packages/work` called `flush_artifacts(timeout=120)` before Trackio's configured 600-second finalization barrier. The first wait timed out; the subsequent failure-finalization drain completed, and reconciliation recorded one required model artifact with consistent failed tracking state.
- Observation: RC3 passed the workload and evidence gates but the workflow classified ordinary cleanup contention as candidate failure.
  Evidence: provider run `pt-631f078dabf5d8084fd84f87` succeeded with required model digest `2968e2f98ed94c48081434570ebe568b377cc3645a5af7c6ff61e374ed5b9e0a`; unrelated occupancy run `pt-9e8dcaafe6c928d186766330` acquired the only worker before exact cleanup task `pt-clean-75f784239e27f314e2` was submitted. The cleanup task remained durably queued under dstack's no-capacity retry policy, and the retained source workspace contained only an empty scratch directory and the terminal marker.

## Decision Log

- Decision: Keep `release/manifest.toml` at `0.4.0` and allocate real `0.4.0rcN` candidates.
  Rationale: RC numbering supports multiple development iterations without consuming or overwriting the stable version.
  Date/Author: 2026-09-11 / Codex with user direction.
- Decision: Do not rename or byte-promote an RC wheel as final.
  Rationale: Python version metadata and exact sibling dependency pins differ between `0.4.0rcN` and `0.4.0`. The final workflow performs a controlled metadata rendering and binds both receipts.
  Date/Author: 2026-09-11 / Codex.
- Decision: Keep runtime-image digests constant across RC and final when runtime inputs are unchanged.
  Rationale: OCI digests, locks, and image receipts are the executable materialization. Candidate numbering is not a runtime-image build input.
  Date/Author: 2026-09-11 / Codex.
- Decision: Registry cleanup starts only after stable v0.4 and rollback verification.
  Rationale: before stable acceptance, candidate and older images may still be needed for diagnosis or rollback. Deleting by age or mutable tag cannot prove safety.
  Date/Author: 2026-09-11 / Codex.
- Decision: Distinguish deferred exact-worker cleanup from fatal cleanup failure at the CLI and release boundary.
  Rationale: the provider already persists one idempotent exact cleanup task for up to 24 hours, while infrastructure owns a terminal-marker-validated retention timer. A busy single-slot worker is therefore temporary scheduling state, not evidence that the candidate workload or artifact lifecycle failed. Fatal scope, identity, or cleanup-command errors continue to fail the release.
  Date/Author: 2026-09-11 / Codex with user direction.

## Context and Orientation

The working checkout is `/home/hammad/projects/rl-local-async` on branch `codex/local-async-source-env`. `release/manifest.toml` owns the stable target. `.github/workflows/release-candidate.yml` owns RC publication and live qualification. `.github/workflows/release.yml` owns stable publication and tagging. `apps/release/src/posttrain_release/candidate.py` allocates unused RC numbers. `apps/release/src/posttrain_release/versioning.py` stages either the authored final version or an RC override. `apps/release/src/posttrain_release/artifacts.py` records distribution hashes. `apps/release/src/posttrain_release/promotion.py` binds candidate and final receipts. `packages/runtime-images/src/posttrain/runtime_images/published.toml` is generated release evidence and must never be hand-edited to make a check pass.

An RC is a PEP 440 prerelease such as `0.4.0rc3`. A release materialization is the accepted source commit plus generated runtime locks, maintained-fork identities, OCI image digests, and distribution receipts. A retention root is any manifest digest that must remain because a supported release, active job, retained rollback, or accepted evidence record references it. Registry garbage collection means deleting unreferenced blobs after manifest deletion; it is distinct from deleting a named manifest and must be run by infrastructure while the registry is in its supported offline maintenance state.

After candidate acceptance, merge only source that is identical to the candidate build inputs except for documented release plumbing and the generated image manifest. It must verify the RC still exists unchanged, restore the accepted locks and manifest, build final `0.4.0` metadata, create a promotion receipt joining candidate and final receipts, publish directly to stable, verify hashes, perform a no-cache stable install, and tag only after all earlier steps succeed.

Cleanup is a separate post-release transaction. Read retention roots from the new stable `published.toml`, the immediately preceding supported stable release selected for rollback, active dstack runs, retained project run manifests, accepted candidate evidence, and the registry-publication controller. Inventory both LAN and cloud-mirrored registries by repository, tag, digest, manifest media type, creation evidence, and compressed bytes. Classify universal base and job-kind images separately from actual-job images. A candidate for deletion must be absent from every root set in both registries and must not be needed by an active or recoverable job.

Generate an immutable cleanup plan containing exact repository and manifest digest pairs, a snapshot digest of all roots, and the expected reclaimed manifest bytes. Review the plan before applying it. Delete tags and manifests by exact identity from both canonical copies, reconcile only their publication-controller rows, and recompute reachability. Run offline blob garbage collection only after the second reachability scan proves blobs unowned. BuildKit cache is a separate optimization surface: preserve shared cache unless a record is uniquely attributable to a rejected image. Record every removed identity, preserved root, actual reclaimed bytes, and post-cleanup digest readback.

The Python development-index cleanup follows the same rule. Preserve the accepted RC receipt and GitHub evidence even if an obsolete package is later removed from the mutable development index. The legacy dev-only `0.4.0` files require a dedicated reviewed migration plan because they collide with the final name; do not delete them during RC preparation or let a broad cleanup command infer authority.

## Validation and Acceptance

Release preparation is accepted when release tests prove RC allocation, promotion rejects a non-RC candidate or mismatched package/image receipts, final source comparison rejects any package-input change, and both candidate and stable installs use only their intended indexes without workspace or Git sources.

The release is accepted when one `0.4.0rcN` candidate has complete retained evidence, stable `0.4.0` installs from a clean environment, every first-party distribution has the coordinated final version, the final tag points at the accepted merged commit, the OCI digests equal the candidate materialization, and one supported packed job completes with Trackio and Observatory readback.

Cleanup is accepted when every preserved stable/rollback/active digest still resolves from both registry paths, every planned obsolete manifest is absent, no active dstack job references a deleted digest, publication-controller state agrees, and the cleanup receipt reports exact deletions and reclaimed bytes. No shared base/kind image or BuildKit cache record may be deleted merely because it is old.

## Idempotence and Recovery

Candidate retries are safe because each run allocates a new RC. Image publication is digest-addressed and reuses verified content. Stable publication is idempotent only when index readback matches the final receipt; a mismatched occupied stable version is terminal and must never be overwritten. If final publication succeeds but tagging fails, resume from retained final evidence rather than rebuilding.

Cleanup planning is read-only and repeatable. Apply must reject a changed root snapshot or stale manifest digest. If deletion stops partway through, retain the partial receipt, recompute reachability, and generate a new plan for the remaining exact identities. Never use broad repository deletion, age-only retention, or recursive BuildKit pruning as recovery.
