# Show how evaluated models behave, not only what they score

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. It follows `docs/templates/PLAN.md` and must be maintained in accordance with it.

## Purpose / Big Picture

Observatory's evaluation ("evals") view compares evaluation runs of one suite, for example a base model and several training checkpoints, by a single score. A score alone often does not explain a result. Two checkpoints with the same held-out score can behave very differently: one may need fewer turns, make fewer tool-call mistakes, or think for half as many tokens, and a score gain can come with more truncation. Researchers on this project repeatedly had to write one-off scripts over raw traces to see those differences.

After this change the evals view shows, for every evaluation run and next to its score: how many turns (model calls) an episode takes, including on episodes that finish on their own; how many tool calls it makes and how many of them the environment counted as mistakes, with the environment's breakdown; how often episodes are truncated and how they end; and how many tokens the model spends thinking and answering. The same numbers appear on the page that compares two runs and on each run's own evaluation page. They also exist for evaluations recorded before this change, through a one-time backfill.

To see it working, open Observatory's Evaluations page for the suite `eval/lfm2.5-2.6b/automationbench-heldout-matched-64k-v4-t05`. The table that lists the base model and checkpoints shows, beside Score, the columns Turns, Turns (completed), Tool calls, Tool mistakes, Truncated, Thinking tokens and Answer tokens, with values for runs such as `eval-lfm26-heldout-64k-v4-t05-base-20260928-r1` and `eval-lfm26-heldout-64k-v4-t05-h100notrunc-step50-20260930-r1`.

## Surprises & Discoveries

- Observation: evaluation traces do not keep the tokens the model generated, so the renderer re-parse that recovers thinking counts for training traces cannot run on them.
  Evidence: in `eval-lfm26-heldout-64k-v4-t05-h100notrunc-step50-20260930-r1`, every assistant node has 10 `token_ids` and no sampled positions, while the calls report 142, 353, 248 and 2661 completion tokens.
- Observation: LFM2.5 evaluation traces record no thinking tokens although the model thinks on every call. The chat template opens `<think>` in the prompt, so the sampled text is "thinking, then `</think>`, then the answer"; vLLM's LFM2 reasoning parser does not split it, reports no `reasoning_tokens`, and leaves `reasoning_content` empty.
  Evidence: `calls[].usage` holds only `prompt_tokens` and `completion_tokens`; `</think>` appears once per call in `nodes[*].message.content`; the projected fact has provenance `thinking_tokens: unsupported`.
- Observation: the LFM2.5 evaluation bindings configure no vLLM reasoning parser, so vLLM returns thinking inside `content` and no reasoning count. Of vLLM's parsers, only `qwen3` counts thinking when the template opened `<think>` in the prompt.
  Evidence: on three real replies (254, 386 and 254 completion tokens), `qwen3.count_reasoning_tokens` gave 177, 302 and 144, and `deepseek_r1` gave 0, 0 and 0. Rendering a history with the thinking inline and without it produced byte-identical prompts.
- Observation: the renderer counts the closing `</think>` token as thinking and vLLM's `qwen3` parser does not, a difference of exactly one token per model call (about 0.3% of thinking on these tasks).
  Evidence: three full eval traces gave renderer versus `qwen3` totals of 4654 vs 4644 (10 calls), 13874 vs 13859 (15 calls) and 7595 vs 7583 (12 calls). Thinking is 61% to 84% of all generated tokens.
- Observation: AutomationBench already counts tool mistakes per episode and records them as native metrics, while raw tool results have no consistent failure shape.
  Evidence: 300 eval traces carry `tool_mistakes`, `tool_invalid_arguments`, `tool_missing_arguments`, `tool_unknown_id`, `tool_unknown_tool`, `tool_empty_results` and `task_completed_correctly` in `raw.metrics`. Their tool results were 2184 `{"success": true}`, 122 `{"success": false, "error": ...}`, 10 `{"error": ...}` without `success`, 81 JSON objects with neither field, and 232 plain-text results.

## Decision Log

- Decision: the environment defines tool-call failure; the framework collects the environment's per-episode numeric metrics and never classifies raw tool results itself.
  Rationale: raw tool results have no common failure shape (see Surprises), and only the environment can tell a model mistake (an invented id) from a legitimate miss (a search that finds nothing). The canonical observation document already lists "`eval/environment/*` env-native diagnostics worth indexing" at the rollout grain, so this realizes an existing field. It also lets another environment bring its own diagnostics without framework changes.
  Date/Author: 2026-10-01, user and Claude.
- Decision: environment metrics are stored as name and value rows in a new Trackio table, not as new fact columns.
  Rationale: fact columns on Trackio's `traces` table are fixed and named by the framework; environment metric names are chosen by each environment. Trackio already stores reward components this way (`trace_reward_components`), so the new table follows an existing, qualified pattern.
  Date/Author: 2026-10-01, Claude.
- Decision: backfill evaluations that were recorded before this change, for both environment metrics and thinking counts.
  Rationale: the comparisons researchers need span existing checkpoints (base, SAMPO r2, the 6e-5, 1e-4 and H100 runs); a view that only fills for new runs would not answer current questions.
  Date/Author: 2026-10-01, user.
- Decision: new LFM2.5 evaluations report thinking through vLLM's `qwen3` reasoning parser, configured on new revisions of the two eval bindings, rather than routing evaluation traffic through the renderer.
  Rationale: it is one line of serving configuration that vLLM already turns into `completion_tokens_details.reasoning_tokens`, which Verifiers and the existing projection read; prompts are unchanged because the chat template strips past thinking; `deepseek_r1` was rejected because it counts zero on replies whose thinking the prompt opened. Existing binding revisions are left unchanged so past evaluations keep their exact configuration.
  Date/Author: 2026-10-01, Claude.
- Decision: thinking counts come from the model's renderer, which already provides them on the training path. For existing evaluation traces, which keep only text, the backfill tokenizes each reply with the renderer's tokenizer and lets the renderer's parser find the thinking boundary, recording the provenance as re-tokenized text.
  Rationale: the renderer is the component that knows each model's thinking markers; hard-coding `</think>` in the projection was deliberately removed at fact calculator v6 and must stay removed. Re-tokenizing decoded text can differ from the sampled tokens by a few tokens per reply, which is why the provenance records it.
  Date/Author: 2026-10-01, user and Claude.

- Observation: a Posttrain client that sends environment metrics to a Trackio server that predates them fails, not silently: the server recomputes each projection identity from the payload and an unknown field changes the identity it expects. Clients must therefore not send environment metrics until the server is upgraded and its database migrated.
  Evidence: `TraceFactUpdate.from_payload` in the dev32 server ignores `environment_metrics` while the client's `projection_id` includes it, so the identity check raises "projection id does not match the immutable trace fact payload". The adapter refuses to build such an update when the installed Trackio lacks the field, but a newer client against an older server cannot detect it, so deployment order matters: migrate and switch the Trackio server first, then roll out clients.
- Observation: Doris run deletion never removed `trace_reward_components` rows.
  Evidence: `delete_run`, `purge_runs` and `delete_project` in `trackio/doris_storage.py` listed the tables to clean without `trace_reward_components`, so every deleted run left orphaned component rows. The change that adds `trace_environment_metrics` fixes both and a unit test covers them.

## Context and Orientation

This repository is a Python 3.12 `uv` workspace (see `AGENTS.md`). The pieces this plan touches fit together as follows.

An evaluation run executes a model on an environment's tasks and records one native trace per episode. An episode is one attempt at one task: the model and the environment exchange messages over several turns (model calls), and the model calls tools, until it finishes or hits a limit. The native trace comes from the Verifiers library and holds the whole transcript (`nodes`), each model call's token usage (`calls[].usage`), and the environment's own per-episode numbers (`metrics`).

When a trace is recorded, `project_verifiers_trace_facts` in `packages/environment/src/posttrain/environment/verifiers_evidence.py` computes trace facts: a small fixed set of dimensions and measures such as `tool_calls`, `model_calls`, `model_output_tokens`, `thinking_tokens`, `is_truncated` and `episode_ending`, plus `provenance` strings that say how each value was obtained. The evaluation adapter calls it in `packages/eval/src/posttrain/eval/backends/verifiers/adapter.py` (around line 241) and hands the facts to the run context, which writes them to Trackio. Trackio is the tracking server (a CarbonTeq fork maintained in the sibling repository `../trackio`, released as the wheel `carbonteq-trackio`, pinned at `0.31.5.post14.dev32` in `packages/tracking-trackio/pyproject.toml`). In production Trackio stores traces in Apache Doris, a SQL database; each fact is a column named `fact_<name>` on the `traces` table. Reward components use a separate table, `trace_reward_components`, with one row per trace and component (`../trackio/trackio/doris_schema.py` around line 105, and `../trackio/trackio/sqlite_storage.py` for the local SQLite backend).

Observatory (`apps/observatory`) is the read-only evidence product. Its semantic layer (`apps/observatory/src/posttrain_observatory/semantic_layer/`) exposes named tables over Trackio data; the `rollouts` table has one row per episode with the columns `run_id`, `task`, `rollout_reward`, `truncated`, `failed`, `ending`, `tool_calls`, `model_calls`, `output_tokens`, `thinking_tokens` and `input_tokens` (declared in `framework.py`; the Trackio column list is in `views.py`). The evals view is served by `evaluation_index` and `evaluation_tasks` in `apps/observatory/src/posttrain_observatory/evaluations.py`, which run the SQL strings `INDEX_SQL` and `TASKS_SQL` over `runs` and `rollouts` and return `EvaluationRecord` and `EvaluationTaskScore` models through `GET /api/v1/evaluations` and `GET /api/v1/evaluations/tasks` (`http.py`). The React frontend renders them in `apps/observatory/frontend/src/components/EvaluationViews.tsx` (`SuiteSection` builds the per-suite table, `EvalComparePage` compares two runs) using types generated from `apps/observatory/openapi.json` into `frontend/src/lib/api-schema.ts` by `npm run generate:api`. A single run's evaluation page (`EvaluationOverview` in `frontend/src/App.tsx`) shows latency, token and tool-call distributions from `TraceEvaluationView.performance`.

The canonical rules for this evidence are in `docs/post-training/06-observation-and-lineage.md`. Two matter here. First, record a value once at the lowest grain (the episode) and compute run-level means and rates in Observatory; never persist a second copy of an aggregate. Second, views read provider-neutral facts, not raw native payloads. That is why tool mistakes, which exist today only inside the payload, must become recorded evidence before the view can show them.

A renderer is the component that turns chat messages into model tokens and parses generated tokens back into thinking, answer and tool calls for one model family; LFM2.5 uses `lfm2.5-tools-thinking@2` (`packages/common/src/posttrain/common/variants/lfm25.py`). On the training path the renderer reports `usage.reasoning_tokens` for each call. `fill_renderer_reasoning_tokens` in `apps/cli/src/posttrain_cli/trace_fact_backfill.py` re-parses a stored call's generated token ids with the renderer to fill that count for older training traces, and `posttrain trace-facts backfill <provider-run-id> [--apply]` re-projects a run's traces in checkpointed pages of at most 1,000 (preview by default).

## Plan of Work

Milestone 1 adds the behaviour columns that existing facts already support, so it needs no new data and immediately covers every recorded evaluation. In `evaluations.py`, extend `INDEX_SQL` and `TASKS_SQL` with per-run (and per-task) means over non-failed episodes: `avg(o.model_calls)` as turns, the same mean restricted to `o.ending = 'completed'` as turns on completed episodes, `avg(o.tool_calls)`, `avg(o.output_tokens)`, and `avg(o.thinking_tokens)` returned as null when every value is missing (never as zero, per the missing-evidence rule). Add a second query grouped by `o.run_id, o.ending` that returns the ending counts per run, attached to each record as a mapping. Add the matching optional fields to `EvaluationRecord` and `EvaluationTaskScore`, regenerate `openapi.json` and `api-schema.ts`, and add columns to the `SuiteSection` table and the comparison page. Missing values render as an em dash with a tooltip naming the reason (for example "not recorded for this run"). Tests: extend `apps/observatory/tests/test_evaluations.py` with fake rows that exercise means, the completed-only mean, null thinking and the ending mapping; extend `EvaluationViews.test.tsx` to assert the new columns and the missing-value rendering.

Milestone 2 makes thinking tokens real. Begin with a prototype that decides how new evaluations report them. Option A patches vLLM's LFM2 reasoning parser, in the vLLM fork the evaluation image uses, so it treats the reply as already inside a thinking block when the chat template opened one in the prompt. vLLM then returns `reasoning_content` and `usage.completion_tokens_details.reasoning_tokens`, and the existing projection records `provider_reasoning_usage`. Option B routes evaluation calls through the renderer, as the training path does. The prototype runs a two-task evaluation of LFM2.5-2.6B each way on the local GPU and compares the counts with the renderer's count on the same replies. Choose A if it matches within one token per reply and needs no Verifiers change; otherwise B. Record the choice in the Decision Log. Then implement the backfill for existing evaluation traces. Move `fill_renderer_reasoning_tokens` and its helpers from `apps/cli` into `posttrain.environment`, next to the projection, and add a text path: when a call's node has no sampled token ids, tokenize the node's message content with the renderer's tokenizer, parse it with `renderer.parse_response` using the ancestor messages as the prompt, and record the count with provenance `renderer_retokenized_text`. Widen `_has_unscored_thinking` so a trace qualifies when its thinking is unsupported and the renderer finds thinking in the content, not only when `reasoning_content` is set. Tests cover both paths, including a fixture reply with `</think>` inside the content and a node without sampled ids.

Milestone 3 records environment metrics, in two repositories and in this order. In the Trackio fork, 3a adds the table `trace_environment_metrics` (columns `project_id`, `trace_id`, `projection_id`, `name`, `run_id`, `value DOUBLE`, unique on project, trace, projection and name) to both `doris_schema.py` and `sqlite_storage.py`. Writes replace a trace's rows for a projection atomically, exactly like reward components. Readers are paged and filtered by run. It also adds the idempotent Doris migration and fork tests, updates `CARBONTEQ_FORK.md` and releases a new dev version. Then, in Posttrain, update the pin in `packages/tracking-trackio/pyproject.toml` and `uv.lock` and update `docs/tooling/trackio/README.md`, per `docs/tooling/forks.md`. In Posttrain, 3b adds `environment_metrics: Mapping[str, float]` to `TraceFactSet` (`packages/common/src/posttrain/common/execution.py`). `project_verifiers_trace_facts` fills it from the native trace's numeric `metrics`, skipping non-finite values and names longer than 256 characters, and bumps the fact calculator version. The Trackio tracking adapter writes and reads the new rows. The semantic layer gets a table `rollout_environment_metrics` (`run_id`, `trace_id`, `name`, `value`) that joins to `rollouts`. The evals view adds a per-run mapping of environment metric means and per-episode "any" rates, which the frontend shows as Tool mistakes (from the environment's `tool_mistakes`) with a breakdown tooltip. The frontend is not specific to AutomationBench: it lists whichever metric names a suite reports, and the suite table shows the metric named `tool_mistakes` when present. Before any code, amend `docs/post-training/06-observation-and-lineage.md` under "Eval metrics" to state how `eval/environment/*` is realized: numeric per-episode environment metrics are recorded once per trace as name and value evidence, the environment owns their names and meaning, and views compute means and rates from them. The trace-fact backfill re-projects existing traces and writes their environment metrics.

Milestone 4 deploys and backfills. Deploy the Trackio release with its migration through the ai-infra playbook for Trackio, then the Observatory build. Run `posttrain trace-facts backfill` in preview and then `--apply` for each evaluation run of the v4 and v4-t05 suites, and check the view.

## Validation and Acceptance

Milestone 1 is accepted when the evals page for suite `automationbench-heldout-matched-64k-v4-t05` shows the new columns for the base run and the H100 step-50 run, and the values match an independent computation over the `rollouts` table (for example the mean `model_calls` per run from the semantic SQL endpoint). New backend and frontend tests fail before the change and pass after. Milestone 2 is accepted when a new LFM2.5 evaluation run records non-zero `thinking_tokens` with provider or renderer provenance, and the backfill fills existing evaluation traces with `renderer_retokenized_text` provenance. On a sample of 20 replies, the backfilled count must be within 2% of the renderer's count computed on the same text. Milestone 3 is accepted when a new evaluation records AutomationBench's `tool_mistakes` per episode, the evals view shows mistakes per episode and the share of episodes with any mistake, and those numbers match the scoring script used on 2026-09-30: base v4-t05 about 1.09 mistakes per episode and 27% of episodes with a mistake. The full validation ladder must pass in every repository touched (`AGENTS.md`).

## Idempotence and Recovery

Milestone 1 changes queries and views only and can be reverted by reverting the commit. The backfill is replay-safe: it previews by default, checkpoints every page of at most 1,000 traces, and re-running it with the same cursor rewrites the same facts. The Trackio migration only adds a table (`CREATE TABLE IF NOT EXISTS`) and never alters existing data. Take the ai-infra Doris backup (`qualify_trackio_doris_backup.py --retain-backup`) before applying it in production.
