Post-training a 4B model on AutomationBench: what we did and why

The goal: make Qwen3.5-4B better at multi-step business workflows without reinforcement learning, measured on 120 test tasks it never trains on. It went from 28.3% to 42.4% with SFT and to 50.6% with one round of SDPO on top, level with Qwen3.5-397B (49.6%). This page explains how the tests were built, how models were scored, and why each method was run the way it was.

The starting point: why the handover's gain did not hold

↑ Map

The handover's best study trained SDPO on a pool of 124 tasks and reported 51.6% to 58.1% on a 62-task heldout set. Reading its records showed why that could not be relied on:

  • One greedy attempt per task. Its 5 repeat runs were identical, so the gain was 4 of 62 tasks flipping.
  • The step was picked after seeing the test scores, and the run crashed after 38 updates.
  • The heldout set was half "simple" tasks (30 of 62), which the benchmark's own score leaves out, and its environment had known task defects.
  • Training attempts were cut at 8 turns while the prompt promises about 50, so many "mistakes" were attempts that ran out of turns.
  • The teacher saw the grader's expected answers, and often the same attempt shown as the "correct solution".
  • No weights, and results only on the workstation.

Retrained twice under the handover's own protocol, the recipe gave 58.1% and 54.0%. At 48 sampled attempts per task, every variant scored slightly below the untrained model (55.8%). Our own SDPO recipes on the same set lowered harmful actions by about 3 points but did not raise success. That is what started the work below.

How the test and training sets were built

↑ Map

Three frozen sets, built once from tasks no model had been run on, with no task in two sets. Their task names and the hash of every task's prompt, data, tools and checks are recorded in fixtures/automationbench/sets-phase2-frozen.json on the SFT branch.

1 · The pool: 364 domain tasks no model had been run onAutomationBench has 600 domain tasks in six areas plus 200 short "simple" ones; the benchmark's score counts only the domain tasks, so simple tasks were left out. Tasks already used by earlier work were set aside for training at most.
2 · Screened: how often does the untrained 4B solve each task?4 untrained attempts per task gave each task a level: never, sometimes (low, middle, high) or always solved. Always-solved tasks were excluded from every set: they cannot show a gain.
3 · Proven solvable: no task the model fails because the task is brokenEvery never-solved candidate had to be solved by a stronger model (Haiku first, then Sonnet or Opus) working through the environment's own tools and grader, never shown the checks or expected values. Tasks no model could solve were read; real defects were fixed in the environment (information the checks need but the task never gave, or a check contradicting the task's own text), never dropped. Each fixed task needed a correct solution that replays at full score. 93 tasks were fixed by 10 Nov; every fix is a commit in the environment pull request.
4 · Split, balanced by domain and by levelPer domain: the test took half of the sometimes-solved tasks (at most 6) plus proven-hard tasks to make 10; a second test-sized set took a quarter (at most 3) plus hard tasks; training got the rest. Near-duplicate tasks (the same workflow in two domains; 9 such pairs) were handled so that no test task has a near-copy in training.
5 · Frozentest120 = the two 60-task sets (10 Nov), 20 tasks per domain; two tasks found always-solved were swapped for same-domain proven-solvable tasks, and 46 test tasks got information-only fixes. guard10 = a fixed-seed draw (seed text "sdpo-ab-20261105-guard:" + domain) of up to 2 never-used, always-solved tasks per domain (sales and support had one each): a warning set, never trained on and never used to choose. train204 = 34 tasks per domain (11 Nov), each proven solvable, 33 of the 84 new ones needing a fix.

SFT: the main gain

↑ Map

Qwen3.5-397B solved the training tasks inside the 4B's own evaluation loop, with the same tools, prompt, limits and thinking. Code checked every solved attempt for grounding, exact values and forbidden actions; 97 rows (one per task) became the data. LoRA SFT on it took the 4B from 28.3% to 42.4% on test120, and the same data and recipe took the 9B from 35.5% to 46.3%. Test tasks closest to a training example gained most.

DPO: tried and closed

↑ Map

Pairs of the SFT model's own passed and failed attempts at the same task (322 pairs on 111 tasks, on the exact tokens it sampled), with the SFT model as the frozen reference. It added 0.9 points. A passed and a failed attempt differ in dozens of ways, so DPO learned habits every passed attempt shared, such as shorter final replies, rather than the decision that failed the task. Published work agrees that DPO on long agent tasks needs thousands of short, single-difference pairs. Closed on 20 Nov; the analysis is chapter 9 of the deep dive.

SDPO: how it works here, and why each setting

↑ Map

SDPO (Hübotter et al., 2026, arXiv 2601.20802) trains the model toward a teacher that is the same model with extra information in its prompt. The student makes an attempt; the teacher re-reads exactly those tokens with the feedback, and wherever it would have chosen differently, the student is pulled toward its choice. No stronger model is involved, so everything rests on the feedback. The paper only covers single-turn tasks; on AutomationBench the feedback has to say at which turn the attempt went wrong.

The feedback engine

A separate library reads one attempt and its task and writes the teacher's feedback:

  1. Record every call, every value the attempt saw, and each grader check that failed, tied to the call and turn where it went wrong.
  2. Check every line: it must be true of the attempt, and must not show a value the attempt never saw.
  3. Write plain lines: what the task forbids, what it still requires, why a tool call failed and which tool finds the right ID.
  4. Place each line as a note at the turn of the first wrong decision; the teacher's first message says only that the attempt failed.

Real feedback from the run that reached 50.6%

Task (shortened): There's a seasonal campaign coming up… get social posts scheduled on the right channels. Double-check any channel guidelines before scheduling. Teacher's first message, after the task: The following are results from your unsuccessful earlier attempt: Its mistake is noted at the step where it happened. Correctly solve the original question. Note before turn 3: Note on your next action: This task forbids buffer_add_to_queue producing a buffer post in channel "ch_linkedin", not every buffer_add_to_queue call. Other kinds of note in the run: google_sheets_find_worksheet returned an error: Worksheet not found in spreadsheet. Use an exact worksheet title or ID. google_sheets_get_spreadsheet_by_id returns a spreadsheet with its worksheets. wave_update_product can change a wave product with id "wp_002"; its field "unit_price" has to stay "4500".

The notes also tell the teacher never to refer to them in any message or record it writes, so the student does not learn to quote feedback it will not have.

Every SDPO run, in order

  • 2–10 NovTwo SDPO runs (R0, R1) on the first fixed test: gains only on the trained tasks; the feedback quoted the answers.
  • 11 NovA guarded run: no gain; SDPO paused, SFT started.
  • 14–15 NovThree arms on the 204-task pool: from SFT, the first held-out gain (+4.2 on H2); from the untrained model, much lower.
  • 16–17 NovTwo full runs from SFT: test120 43.7% and 45.3% (+1.3 and +2.9 over SFT).
  • 20 NovA pilot with rewritten feedback: +5.2 on H2, but guard10 fell 13.75 points, so its gate failed.
  • 20–22 Nov15 rounds of feedback rewriting against explicit requirements (useful to a 4B teacher, true, never forbidding what the task needs, easy to act on), each screened by how often the teacher then solved the task.
  • 22–23 NovThree rounds with that feedback: round 3 reached 45.4%; round 1, picked on H2, reached 50.6% (+8.2, measured).
  • 24 NovOne more feedback version, one round: 31.7% on H2, below round 1's 34.4%, so it stopped there.

What the results taught

↑ Map
  1. LESSON 1

    Measure with many attempts, compared task by task

    One greedy attempt per task gives one yes or no per task; the handover's gain was 4 tasks.

    What to keep doing

    8 attempts per task on 120 frozen test tasks, the same tasks before and after.

  2. LESSON 2

    Fix the tasks before training on them

    Many never-solved tasks were broken: information missing, or checks that contradicted the task.

    What to keep doing

    Fix every defect with a replayed proof; never drop a task to raise a score.

  3. LESSON 3

    Data must look like the student's own work

    Examples without planning text made the 4B worse; the same tasks solved in its own loop with reasoning made it better.

    What to keep doing

    Generate data inside the student's evaluation loop and check every row by code.

  4. LESSON 4

    Feedback that quotes answers teaches only those tasks

    Early SDPO gains stayed on the trained tasks.

    What to keep doing

    Hide values the attempt never saw; say where the value lives instead.

  5. LESSON 5

    Judge feedback by what training does with it

    For over a week feedback was judged by how often the teacher then solved the task; that did not predict training gains.

    What to keep doing

    Pick feedback and rounds by a held-out training result fixed in advance.

  6. LESSON 6

    Check that the adapter is really loaded

    Two framework paths silently dropped every LoRA weight (wrong model class); results looked like the base model.

    What to keep doing

    Load Qwen3.5 adapters with the image-text class and check that scores change.

Open questions

A second SDPO seed

SFT on data version 4

102 rows, accepted and never trained; the natural next SFT run.

SDPO on the 9B

The SFT gain carried to the 9B; SDPO from the 9B SFT adapter is untested.

The guard10 drop

SDPO's warning-set score fell from 78.8% to 66.3%; which tasks fell, and why, was not traced.

Feedback that says why

The grader's checks name what is missing, not why. Some teacher retries did the named thing and skipped the step the task needed.
