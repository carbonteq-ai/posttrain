# Posttrain v0.4 release notes

Posttrain v0.4 gives you faster training recipes and a clearer view of what
your agent did. One tested LFM2.5-2.6B VORTEX recipe dropped from 823 to 276
seconds per update through less padding, decoder compilation, and DSpark
rollout. The gains depend on the model, hardware, and settings.

VORTEX fills updates with attempts that earn different rewards, so the learner
has a useful comparison. SAMPO can learn from progress at individual turns
using the environment's own rewards. Both run on TRL and veRL in v0.4.13.

In Observatory, you can follow an episode's tool calls, see why it ended,
and compare checkpoints with their base model. Run notes keep your explanation
beside the evidence, including SQL results you can reuse in the text.

The latest stable release is [v0.4.16](https://github.com/carbonteq-ai/posttrain/releases/tag/v0.4.16),
published October 8, 2026. The v0.4 series covers seventeen releases.

## Features

### Install anywhere, evaluate faster (v0.4.16)

From v0.4.16 the release wheelhouse carries the wheels of the maintained forks
it depends on, so it installs with public PyPI alone; the release candidate
proves this with a clean install that sees only `pypi.org`. See the
[installation guide](../install.md).

AutomationBench evaluations take 9-13 minutes instead of about 23: compiler
caches persist between jobs (engine start 13.5 s instead of 111 s), traces are
published compressed, and Verifiers `0.3.2.dev109` stores assessment history
compactly (a 100-episode trace file drops from 902 MB to 140 MB) and retries
model calls whose connection closed early, so no attempts are dropped.
Environments `carbonteq-2026.10.08` fix eleven manifest checks that could not
credit correct work; goal rates rise 6-8 points for the same episodes, so
re-baseline earlier evaluations.

### Faster training, rollouts, and evidence access

Speedups in v0.4 come from several parts of the workflow: less work per actor
update, faster token generation, reuse of cached prefixes, smaller evidence
uploads, and narrower queries. The measured LFM2.5-2.6B VORTEX recipe went from
about 823 to 276 seconds per update, roughly 3x faster.

#### Fill useful updates with less refill work

VORTEX's yield-first curriculum samples tasks by their estimated probability
of producing a useful prompt group. Finding useful groups earlier can avoid
spending rollouts on tied-reward groups that must be replaced before the
optimizer update. The exploration lane keeps tasks eligible for rechecking
as the policy changes.

Active-sampling oversampling adds another way to reduce sequential refill
rounds: collect extra groups in the initial round and each refill, retain the
required useful population, and discard the surplus. It trades extra candidate
work and concurrent capacity for fewer collection rounds; it does not guarantee
fewer generated episodes. This applies to the supported TRL active-sampling
paths, including VORTEX and SAMPO.

The recorded runs show the benefit at the recipe level. An earlier random
versus adaptive sampling comparison averaged 5.55 versus 2.05 rounds per update,
with whole-update time falling from 1,270 to 757 seconds, about 1.68x faster.
In the recent SAMPO comparison, the oversampled run filled 95 of 100 updates
in one round, versus 7 of 39 updates in the earlier fixed-tools continuation;
mean rollout time was 222 versus 282 seconds.

| Recorded comparison | Mean refill rounds before → after | Extra candidate episodes per update before → after | Rollout seconds before → after | Completion-token work change at a common effective rate |
| --- | --- | --- | --- | --- |
| Random → adaptive, 20 updates each | 4.55 → 1.05 | 44.4 → 7.8 | 1121 → 629 | 49% less work |
| VORTEX v3 (4K) → v4 (8K), 20 updates each | 2.60 → 1.55 | 24.2 → 13.8 | 615 → 562 | 5% more work |
| SAMPO continuation → FP16/base with oversampling, 39 → 100 updates | 0.923 → 0.050 | 12.0 → 25.9 | 282 → 222 | 16% more work |

Refill rounds exclude the initial collection round. Extra episodes are all
candidate attempts above the configured useful population, including surplus
from initial oversampling. The token adjustment holds each pair's earlier
effective rollout rate constant. This rate includes tools and concurrency;
completion-token work includes tool observations. It is a work comparison,
not a controlled decoding benchmark. The recent oversampled run finishes
rollouts sooner while doing more token work. The earlier adaptive run also
cuts measured refill-only time from 840 to 312 seconds per update.

These are observed recipe comparisons. Framework revisions differ in the first
pair; the SAMPO pair also changes precision, starting checkpoint, sampling
temperature and concurrent capacity. The entire timing improvement cannot be
attributed to curriculum or oversampling alone. Fewer refills do not by
themselves establish faster learning or the same final model quality. See
[the run identities, configuration differences and calculation](v0.4-refill-evidence.md).

#### Spend less time on the actor update

TRL scores each micro-batch at its actual length instead of padding every
micro-batch to the generation batch's maximum. The tested workload had about
9.7K real tokens against roughly 25K padded tokens. Optional decoder-layer
compilation, gradient checkpointing only for long micro-batches, and reuse of
training-forward log probabilities also reduce work.

The Qwen3.5 runtime now includes fast Gated DeltaNet kernels instead of the
Torch fallback. That improvement has a separate measurement on an RTX 3070 Ti.

| Measured path | Before | After | Approximate speedup |
| --- | --- | --- | --- |
| LFM2.5-2.6B VORTEX whole update | 823 s | 276 s | 3.0x |
| LFM2.5-2.6B actor update, 64 episodes | 373 s | 114 s | 3.3x |
| LFM2.5-2.6B rollout, 64 episodes | 334 s | 158 s | 2.1x |
| Qwen3.5-0.8B LoRA actor step, 4,096 tokens, RTX 3070 Ti | 5.0 s | 1.5 s | 3.3x |

The first three rows describe parts of one recipe; their speedup factors are
not additive. The Qwen measurement covers an actor step on different hardware.
These results do not establish the same gains for other models or settings.

#### Generate rollouts faster and reuse prefixes

v0.4 adds DSpark and Uno speculative rollout selections. In the measured LFM2.5
recipe, DSpark ran at concurrency 64 with a 13.75 GiB KV cache and 26% draft
acceptance. A separate 32-episode DSpark replay took 46 seconds against 84 to 87
seconds without speculation.

Prefix reuse avoids recomputing cached context. DFlash and DSpark retain their
trailing prefix-cache block, and session-aware eviction releases cache when a
session finishes. Serving enables prefix caching by default when the binding
omits that setting.

Support depends on the model, backend, and hardware. Unsupported combinations
fail before submission. Uno full-weight/QLoRA refresh and Gemma-on-SM120-FA4
remain outside the qualified paths described by these releases.

#### Use the tuned SM120 rollout path

On SM120 GPUs such as the RTX PRO 6000, you can select a runtime tuned for
the hardware. The vLLM fork includes
shape-tuned BF16 linear kernels, a generic batch-invariant matrix-multiplication
rule, batch-invariant split-KV attention, Gated DeltaNet chunk alignment, and
invariant CUDA RMSNorm. These improve the selected runtime while preserving
its batch-invariance contract; they are not a measured speedup for every model.

An optional `SM120_FA4` paged-attention backend is available for the qualified
Uno path. Its release-clean RTX PRO test at concurrency four recorded 435.78
output tokens/s with zero preemptions. Target decode uses CUDA graphs while
the Uno proposer stays eager. This is an absolute throughput result, not a
matched before/after speedup.

Precision and model support still matter. The tuned batch-invariant linear
configurations are BF16-only; FP16 uses the untuned default. Native FA4 is
rejected on SM120, and the separate `SM120_FA4` backend does not qualify Gemma:
Gemma retains its qualified Triton attention path. Uno full-weight and QLoRA
refresh remain unqualified.

#### Read evidence with less repeated work

Refresh a large run without rereading every finished step. Observatory caches
finished steps and reads only changed steps.
Server-backed trace filters and indexed prompt-group facts narrow the evidence
read. Semantic SQL computes inside Trackio storage and reads only the columns
the statement needs. These are shipped reductions in repeated work; the release
does not provide a comparable query-latency benchmark.

#### Deliver smaller trace artifacts

One 150-update run's final upload fell from 7.7 GB to about 0.7 GB, roughly
91% less data to transfer. Training publishes compressed native episodes and
no longer uploads a second derived trace population. Gzip makes native episode
envelopes about 5x smaller; hashing streams the artifact without loading it
all into memory. These measurements describe artifact size and upload volume;
transfer speed was not measured.

### Train on groups that carry a learning signal

#### VORTEX and adaptive curriculum

Consider four attempts at the same task. Rewards of 0, 0, 0, 0 provide no
group-relative learning signal; rewards of 0, 0, 1, 1 do. VORTEX keeps the useful
group and replaces an uninformative group from a bounded candidate pool before
the optimizer update.

VORTEX means Variance-Oriented Refill and Task Exploration. The recipe combines
the OLMo 3 RL objective with active sampling, an adaptive curriculum, truncation
shaping, and a KL penalty. Refill rounds form one logical optimizer population;
they do not become separate optimizer updates.

Since v0.4.5, the yield-first curriculum samples the full task inventory by the
estimated probability of a useful group, with a default 20% exploration lane.
It checkpoints its state and can warm-start from another run. A task may appear
only once within an optimizer step, including refill rounds; exhausting distinct
tasks is a capacity error. v0.4.12 adds initial-round and refill oversampling,
and v0.4.13 makes the recipe available on veRL as well as TRL.

The initial v0.4.2 AutomationBench profile completed a bounded 20-update
qualification without failed rollouts. Its final 12.5% completion-truncation
observation remains a warning. Later recipes change models, budgets, sampling,
and tools, so that result does not qualify every VORTEX selection.

#### SAMPO and per-turn credit

Train on progress within an episode, including turns that led toward the
result. `train.sampo` assigns credit at episode and turn level. Since v0.4.9
it uses active sampling and can select the adaptive curriculum. v0.4.10
projects AutomationBench's native per-turn progress into rewards, so that
selection can train without an auxiliary judge. v0.4.13 adds veRL support.

The native AutomationBench turn signal is the change in partial credit minus
0.05 per failed tool call. This is environment reward meaning, separate from
the training algorithm. Changing the environment or projection changes the
experiment and must remain visible in its resolved selections.

#### veRL behavior changes in v0.4.13

veRL now applies GRPO/DAPO settings with the semantics selected by the
framework: plain asymmetric token clipping, unclamped k3 KL, declared sampler
correction, TRL-compatible advantage statistics, and complete-group retry and
admission. Rollout temperature, top-p, top-k, repetition penalty, rendering,
tool-call admission, and context limits follow the binding rather than veRL
defaults. New runs record `verl_semantics: trl-parity-v1`.

**Earlier veRL GRPO runs are not numerically comparable with these runs.**
The semantic fixes can change the learning trajectory even when authored
settings look unchanged.

Four matched comparisons covered VORTEX and SAMPO on Qwen3.5-0.8B and
LFM2.5-1.2B. All eight runs completed four updates on the RTX PRO 6000;
first-turn prompt token counts matched, and update-1 rewards over shared tasks
differed by at most 1.60 combined standard errors. This is bounded integration
evidence. It does not establish identical trajectories, convergence, or 8 GB
veRL support: the veRL actor update exceeded memory on the 8 GB card. Qwen
VORTEX sampled-token counts also missed the 15% comparison target, and entropy
aggregations weight sequences differently. See the
[comparison evidence](../plan/verl-vortex-port.md#artifacts-and-notes).

#### Structured credit and asynchronous learning

`train.gdpo` preserves named reward components, normalizes each within complete
prompt groups, combines them with explicit weights, and applies batch-level
normalization. `train.capo` aligns outcome and critique evidence to the original
sampled policy tokens; tool observations and padding are not policy-gradient
coordinates. TRL and veRL adapters preserve scorer/projection identities,
token masks, and checkpoint compatibility.

Native asynchronous Verifiers collection for TRL retains complete groups,
behavior log probabilities, policy-version spans, cancellation, and recovery
of generated but unconsumed groups. Staleness, consumption, and weight updates
belong to the learner. Concurrent environment requests and bounded refill do
not by themselves establish an asynchronous learner mode.

**GDPO, CAPO, and public asynchronous training remain experimental.** Their
plans retain open packaged GPU, scorer, recovery, exported-inference, and async
2B learner gates. Judge composition supports attached, managed, and hosted
inference with explicit model/provider selection and bounded paid cost;
schema-valid judge output alone does not establish judge quality.

### Keep the explanation beside the run

Keep the reason for an experiment beside its results. v0.4.11 adds Markdown
run notes with revision history, so you can record what changed, why you tried
it, and what you learned, then correct the interpretation as evidence arrives.

Notes can include named SQL blocks, render their results as charts, tables,
or single values, and use those results in the prose. For example, a note
about rising truncation can show the relevant update range beside your
interpretation. References such as `{{block.column}}` and
`{{run.<dimension>}}` pull in queried values and run details;
`[[run:id]]` links to another run.

Every job kind also has a run card built from its recorded data. Group-policy
and SAMPO cards summarize reward and entropy over the first and last ten
updates, the best ten-update window, recent KL and truncation, and any recorded
error. The Notes tab puts the card and your explanation together. Notes are
available through Observatory, HTTP, MCP, and `posttrain run note`;
`posttrain run card` renders the card from the CLI.

### Inspect the episode and compare the checkpoint

#### Query the evidence behind a result

Ask a question about your runs without exporting and joining their metrics
yourself. The semantic layer exposes `runs`, `updates`, and `rollouts` as SQL
tables through `posttrain query`, HTTP, and MCP. You can use SQL or the short
`measures`/`by`/`where` form. Results include the executed SQL, so you can inspect
the calculation behind a chart or claim.

Queries run inside Trackio storage, using Doris SQL or translated queries on
local SQLite storage, and compute only the columns the statement reads. One
metric catalog defines the measures used by queries and job views. Missing
evidence stays explicit.

#### Compare a checkpoint with its base model

See whether a checkpoint improved on the base model, overall and per task.
Checkpoint evaluations sit beneath their training run in the sidebar, with
the suite and score visible. The run's Evals tab compares each recorded
checkpoint step with the base model. The Evals page also compares two training
runs of the same base model on a suite they share.

Manifest-backed task selection and held-out AutomationBench measurement
preserve reward, success predicates, errors, truncations, and coverage
separately. Context exhaustion retains scored reward and is reported as
truncation; wholly failed evaluations fail after preserving their evidence.

#### Follow a rollout turn by turn

Find the call that failed or the tool that held up an episode. Transcripts
pair each tool call with its result, timing, token counts, and failures.
A pinned turn index and timeline jumps help you navigate long episodes.
The trajectory timeline separates setup, model generation, tool execution,
and scoring, so you can see where the time went.

Filter traces by step, slice, outcome, or text, with newest results first.
Task and prompt-group reward statistics help explain the individual episode
in the context of the run. Renderer-derived thinking-token counts and explicit
endings distinguish completion, turn limits, token budgets, rejected context,
and errors.

#### See how sampling and credit affect the update

Check whether refill work is producing useful training groups. Active-sampling
views show useful and tied groups, kept and discarded candidates, refill
rounds, and first versus repeated sampling. Curriculum selections and a shared
step range let you follow changes in the collected population across updates.

SAMPO now has the GRPO overview plus a Hierarchical credit tab. It shows episode
and turn credit magnitudes, the turn share of credit, turns receiving credit,
and turns without a peer. Those measures reveal behavior that mean advantages,
which are zero by construction, cannot explain. The Policy optimization
swimlane brings tool failure rate, rollout behavior, update stability,
population, actor and optimizer timing, freshness, and acceleration together.
Each tab names metrics the run did not record.

#### Read larger runs without losing your place

Keep your place while browsing large runs. Tables paginate and sort by column;
note tables also filter rows. Trace navigation loads older rows when needed.
Notes fit the page width, long table prose wraps, and the first column stays
pinned during sideways scrolling. Chart lanes share a step range, with shorter
axis labels near zero. Full run IDs distinguish similarly named evaluations.

Observatory also exposes the configuration review for the run, including
findings and acknowledged exceptions with their reasons. Native Verifiers
episodes remain the replay authority, published compressed without a duplicate
derived trace upload.

### Safer recovery and runtime configuration

Check your settings before spending a GPU run on them. `posttrain.advisor`
and `posttrain settings suggest` identify performance findings before
submission and help size engine settings for the selected model and hardware.

v0.4.12 adds FP16 LoRA training with dynamic loss scaling, float32 loss
arithmetic, loss-scale/skipped-step metrics, and fast Qwen3.5 kernels.
v0.4.13 selects TRL 1.12.0.post12, which carries the float32 arithmetic fix.
See [LoRA for RL](../techniques/grpo/lora-rl.md) for the evidence behind rank,
alpha, learning-rate, precision, and KL choices.

Cancellation on TRL online-RL jobs saves and publishes the last completed
update when newer than the periodic checkpoint. Local cancellation gives
finalization 300 seconds, and cleanup retains checkpoints a stopped worker
could not finalize. Continued LoRA training defaults to KL against the base
model; `kl_reference: start` preserves TRL's former reference, while veRL
rejects that selection for a continued adapter.

Containers receive explicit shared memory: normally 16 GiB, capped by a
declared host-memory budget unless the target specifies a compatible size.
The runtime checks the actual size before execution. RunPod may set shared
memory independently of the requested dstack value, so qualify the intended
provider. Artifact retries, trace delivery, terminal tracking, and queued
cleanup also receive fixes across the series.

### Developer tools and release workflow

- Publish the runtime you verified. Hash-addressed materialization receipts
  bind runtime locks and image manifests to the accepted source, version,
  readiness receipt, and exact file contents. Final publication consumes that
  verified materialization (v0.4.2).
- Release without reserving a GPU for the packaging workflow. Since v0.4.11,
  the candidate workflow builds, verifies, installs from the development index,
  and publishes without a GPU canary. Its GPU qualification inputs and
  capacity-check script were removed. Capability qualification remains separate.
- Use gates that match the current SAMPO recipe. v0.4.9 removes `sampo-extended`,
  `automationbench-sampo`, and four legacy `verl-sampo*` gates that no longer
  match the active-sampling contract. v0.4.13's veRL implementation has its own
  matched comparison evidence.
- Run repeatable diagnostics. Go Task entrypoints support quality and
  release dispatch commands; the configuration advisor and settings calculator
  explain findings before submission. Written acknowledgements document
  performance exceptions. Controllers now report why runs need attention.
- Follow documented recovery and comparison procedures. Orphan-run purge, renderer-aware
  trace-fact backfill, base/checkpoint evaluation selections, and LoRA-for-RL
  guidance accompany the new surfaces. Versioned Lab work packages retain
  bounded comparison settings and exact environment selections.
- Upgrade the runtime components together. The Torch 2.13/CUDA 13 closure, maintained fork
  versions, changed veRL semantics, and AutomationBench tool behavior require
  coordinated upgrades. Use the component table and upgrade steps below;
  historical patch notes describe the choices at that patch, not the final
  v0.4.13 configuration.

## Bug fixes

Some fixes change how you should interpret older results. veRL math rewards
could be zero for correct answers, its KL metric measured the wrong reference,
and fused-layer LoRA synchronization could load incorrect weights. AutomationBench
tool fixes also change evaluation conditions. Establish new baselines for the
affected paths; upgrading does not repair historical evidence.

### Training correctness and stability

- **Math rewards on veRL:** correct GSM8K answers were scored as zero because
  the timeout used a main-thread-only signal inside a Ray actor. Scoring now
  runs in a worker process that preserves the timeout (v0.4.12).
- **LoRA weight synchronization:** fused-layer name mapping could collapse
  distinct adapter tensors, crashing rollout or loading incorrect weights.
  The veRL fork now uses vLLM's rename-only adapter mapper (v0.4.12).
- **FP16 NaNs and skipped updates:** half-precision probability ratios and
  masked loss arithmetic could overflow, causing every update of the SAMPO
  canary to be skipped. FP16 uses float32 logits and loss arithmetic; fused
  optimizer overflow is handled and recorded. The initial loss scale drops
  from 65536 to 1024 to reduce avoidable early skipped steps (v0.4.12;
  TRL's upstream-in-fork arithmetic fix is selected in v0.4.13).
- **Oversampled first rounds:** the rollout row limit rejected the extra groups
  that oversampling requested, so affected OLMo 3 and SAMPO runs failed before
  their first update. Collection now accepts the declared round size (v0.4.12).
- **Speculative rollout observation:** SAMPO, GDPO, and CAPO rejected their
  first TRL update when DSpark/MTP counters appeared. Observation expectations
  now include the selected speculative engine (v0.4.11).
- **veRL sampling and policy semantics:** selected temperature, top-p, top-k,
  repetition penalty, clipping, KL, sampler correction, and advantage statistics
  were ignored or differed from the declared contract. The settings now apply,
  and new runs identify the corrected semantics (v0.4.13).
- **Prematurely rejected veRL episodes:** the worker treated the per-reply cap
  as the whole response budget. It now bounds trajectories by rollout context
  and each reply by its reply cap; over-context next turns end as
  `context_rejected` instead of an episode failure (v0.4.13).
- **Post-training veRL failures:** reward enrichment sent a forbidden
  `rollout_step` field, and curriculum replay could emit decreasing metric
  steps. Reward enrichment now carries only algorithm reward, and curriculum
  records are interleaved in step order (v0.4.12 to v0.4.13).
- **Error diagnosis:** rollout shutdown errors no longer hide the original
  training error; cached GPU memory is released before an asynchronous
  collection wakes vLLM (v0.4.9).

### Environment tools, rendering, and evaluation

- **AutomationBench tools:** Sheets row search now searches instead of returning
  the first ten rows; Drive search excludes placeholder files; Salesforce search
  works without a field name; list arguments preserve their types; and Sheets
  updates remain available to grading. Graders are unchanged, but results need
  new baselines because tool behavior changed (v0.4.12).
- **Training versus serving tool calls:** LFM2.5 training dropped malformed
  Python-style calls that serving repaired and executed. The shared renderer
  now applies the same repairs. veRL additionally uses the same tool wire
  shapes, renderer, stop tokens, and call-admission behavior as the Verifiers
  train client (v0.4.9, v0.4.13).
- **Managed evaluation startup:** the harness used a dictionary operation on
  Verifiers' new lock object, failing every rollout. The runtime is compatible
  with the new lock interface (v0.4.9).
- **Scoring after a failed call:** a GSM8K error could poison subsequent calls
  with an event-loop ownership error. Later scoring calls now remain usable
  (v0.4.7).
- **Context exhaustion:** an evaluation that runs out of context is recorded as
  truncated and keeps its scored reward. A wholly failed evaluation records
  its evidence and then fails instead of presenting a successful run (v0.4.9).
- **Trace message attribution:** veRL bridged turns supplied spans only for new
  messages, attributing tool-result tokens to the wrong messages. Spans now
  cover the conversation correctly; sampled tokens and loss masks were
  unaffected by this display/provenance defect (v0.4.12).

### Metrics, traces, and Observatory

- **Missing traces:** a failed request grew into an oversized resend buffer and
  was eventually dropped; one affected run lost 7,546 of 11,876 traces.
  Trackio now sends bounded requests and retains unsent entries (v0.4.11).
- **Incorrect rollout totals:** separate rollout batches with equal values were
  merged, undercounting episodes and time. Distinct batches remain distinct
  (v0.4.11).
- **Wrong KL metric on veRL:** the reported value was KL to the rollout policy,
  often zero, rather than KL to the reference. It now reads reference KL
  (`actor/kl_loss`) (v0.4.12).
- **Missing training token counts:** Observatory now fills thinking/output tokens
  and turns from stored trace facts when provider usage is absent (v0.4.11).
- **Missing GPU/CPU metrics:** monitoring now starts for new and recovering
  training runs, and SFT/DPO/veRL images include the missing GPU-monitor
  dependency (v0.4.11).
- **Wrong query source:** semantic queries could silently read an unrelated
  discovered tracking project. Queries now use the explicit source, configured
  default, or sole source, and reject unresolved ambiguity (v0.4.12).
- **Missing cancellation metric:** recording the checkpoint metric at an older
  step made tracking reject it. The metric now uses the interrupted update's
  step, with any remaining metric error recorded in the cancel event (v0.4.12).

### Packaging and runtime startup

- **Portable environment packing:** the renderers dependency leaked an internal
  index URL into the environment lock and blocked jobs on v0.4.5. Runtime kinds
  now declare the provided renderers dependency, and source-checkout image pins
  match the published locks (v0.4.6).
- **veRL startup defaults:** jobs without `rollout_execution` failed because
  agent-loop capacity keys were absent from the trainer config. The fork now
  declares compatible defaults (v0.4.12).
- **Insufficient shared memory:** Docker/dstack's 64 MiB default could not hold
  vLLM's 160 MiB broadcast queue. Containers receive explicit shared memory and
  fail early with required/actual sizes when a provider supplies too little
  (v0.4.12).
- **Packaged worker source identity:** veRL now reads the packaged source marker
  instead of requiring Git in the runtime (v0.4.12).
- **Harness dependency drift:** training runs use scripts and dependencies from
  the job's locked environment instead of installing them from PyPI on the
  first rollout. The GRPO starter also uses local subprocesses and checks its
  dataset at job start (v0.4.7, v0.4.12).
- **Environment compatibility:** veRL's control/backend environments now select
  the same Verifiers/renderers closure; catalog agent seats declare the harness,
  timeouts, and turn/token limits required by the pinned Verifiers (v0.4.12).

### Recovery, cleanup, and artifact delivery

- **Checkpoint ambiguity on resume:** an interrupted run could re-publish the
  same checkpoint step. Resume now selects the committed checkpoint (v0.4.8).
- **Checkpoints during cancellation:** local cancellation allows 300 seconds for
  save/publication/finalization, and cleanup retains checkpoints an interrupted
  worker could not finalize. Unreadable checkpoint directories stop cleanup
  rather than allowing deletion (v0.4.12).
- **Stuck local GPU placement:** a failed-versus-cancelled run with no outputs
  could hold its placement indefinitely. Cleanup now releases it (v0.4.7).
- **Stuck dstack cleanup:** scientific-notation byte counts, delayed logs, or a
  missing log from a finished task prevented cleanup completion. Whole-byte
  output, compatible parsing, and late-log handling fix that path (v0.4.12).
- **Long or queued artifact uploads:** expired signed part URLs caused 403s,
  and queued uploads timed out while waiting. Trackio renews signatures and
  measures stalled transfer time; artifact commits retry while the server is
  slow (v0.4.11 to v0.4.12).
- **Terminal status after publication errors:** failed/cancelled runs flush their
  terminal tracking state before surfacing an artifact-drain error; finalization
  uses the tracking backend's configured deadline (v0.4.0).
- **Queued provider cleanup:** temporary capacity deferral is distinguished from
  fatal cleanup failure, and exact-worker cleanup gets highest scheduler
  priority (v0.4.0).

## Upgrade to v0.4.13

Use one complete release wheelhouse and its matching constraints, or the
organization's stable index. Follow [UPGRADING.md](../../UPGRADING.md) for
archive checksum verification, a fresh Python 3.13 consumer environment,
project validation, and rollback. Re-pack jobs to pick up runtime changes.

Before running against shared services:

1. Deploy Trackio `0.31.5.post14.dev32` and migrate Doris to schema version 5
   before jobs write episode-ending facts. This includes the SQL/notes APIs
   introduced with dev31 and schema version 4.
2. Deploy Observatory separately from the desired framework commit; publishing
   Posttrain does not update the running evidence service.
3. When Observatory discovers several tracking projects, set
   `POSTTRAIN_OBSERVATORY_DEFAULT_SOURCE` or the configured Trackio project.
   Ambiguous semantic queries now fail instead of reading an unrelated project.
4. Backfill older trace facts when needed with `posttrain trace-facts backfill`;
   use the documented `--renderer-model` path for historical thinking-token
   counts and review the proposed changes before applying them.
5. Re-establish baselines for changed veRL semantics and AutomationBench tools.
   AutomationBench 0.5.0 fixes tool behavior without changing graders; scores
   on the fixed tools are not comparable with earlier suites.
