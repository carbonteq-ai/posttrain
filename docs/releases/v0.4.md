# Posttrain v0.4

**Status:** release target allocated as `0.4.0`; qualification and publication
are not complete. Development qualification uses immutable `0.4.0rcN`
packages; stable `0.4.0` is rendered only from an accepted RC materialization.

Posttrain v0.4 is the structured-credit and asynchronous-agent release line. It
adds GDPO and CAPO as distinct training operations, preserves the exact reward
and token evidence their credit assignment requires, and connects Verifiers
agent environments to native asynchronous training machinery without making
Verifiers own learner policy.

## Intended release surface

### Structured-credit algorithms

`train.gdpo` consumes ordered named episode reward components with explicit
weights. The algorithm normalizes each component within a complete prompt group,
combines the normalized components, and performs the required batch-level
normalization without collapsing the original evidence vector.

`train.capo` consumes verified outcome and critique evidence aligned to the
original sampled policy tokens. Tool observations and padding remain context,
not policy-gradient coordinates. Both operations retain scorer identity,
projection identity, sampled token IDs, masks, checkpoint compatibility, and
backend numerical settings.

TRL and veRL adapters exist for both operations. Support is claimed per
qualified algorithm/backend cell, not inferred from registration or a source
test.

### Asynchronous agent collection

The release candidate provides a native Verifiers producer for TRL's async GRPO
learner. Independent environment workers can finish agent episodes out of order
while one continuously scheduled inference owner serves model turns. Complete
prompt groups carry exact behavior log probabilities and served policy-version
spans into the learner.

Staleness policy, sample consumption, weight publication, and credit assignment
remain training-backend responsibilities. Verifiers owns task execution, native
episodes, traces, scorer plugins, and acknowledged cancellation. Generated but
unconsumed groups are replayable after checkpoint recovery; partially consumed
groups are rejected rather than silently duplicated.

veRL continues to use its native Ray agent-loop workers and asynchronous rollout
manager. The two backends share evidence and failure semantics, not one process
manager or one weight-update strategy.

### Configuration and execution experience

Planning now reports model-, job-, algorithm-, inference-, update-, and
hardware-related configuration issues before submission. It distinguishes a
wrong configuration from a merely conservative default and allows an explicit,
auditable bypass only for optional readiness probes. Local backend source
capsules let a developer test exact checkout changes in a packaged job without
publishing temporary dependency artifacts.

Production admission remains inventory-driven. The infrastructure repository
owns the concrete dstack fleet; the release target is qualified against named
hardware profiles and sanitized live capacity rather than embedding provider
inventory in reusable framework packages.

## Qualification boundary

The current source has deterministic contract coverage and a real
parameter-changing asynchronous TRL update composed from local source. It does
not yet justify a public async mode. Before `0.4.0` can be published:

1. Complete live async failure-path and checkpoint/resume qualification.
2. Pass the bounded 2B asynchronous learner job from the final packaged image.
3. Close each intended GDPO/CAPO TRL and veRL qualification cell, including
   scorer behavior, optimizer update, recovery, and exported inference.
4. Publish and pin every maintained fork, then generate the runtime-image
   manifest from the final candidate commit.
5. Run deterministic release readiness, the clean consumer install, the packed
   dstack GPU canary, and Trackio/Observatory evidence readback before promotion.

Until those gates pass, synchronous v0.3 behavior remains the supported public
path and v0.4 capabilities are release-candidate functionality.

## Frozen candidate capability matrix

The source boundary for the first v0.4 RC is frozen as follows. “Implemented”
means the operation and adapter contract exist and pass deterministic tests;
it does not mean the cell may be advertised as stable.

| Capability | TRL | veRL | Stable claim at RC preparation |
| --- | --- | --- | --- |
| GDPO structured episode credit | Implemented; five-update toy and numerical evidence retained | Implemented; five-update deterministic evidence retained | Not yet—final packaged GPU qualification remains open |
| CAPO critique-to-token credit | Implemented; five-update toy and mask/export evidence retained | Implemented; five-update deterministic evidence retained | Not yet—final packaged GPU qualification remains open |
| Native asynchronous agent collection | One parameter-changing local update and a 64-trajectory worker run retained | Uses veRL's native Ray agent-loop ownership rather than the TRL worker protocol | Not yet—failure-path, resume, and packaged 2B gates remain open |
| Provider-neutral episode judge composition | Implemented for attached, managed, and hosted inference with bounded cost and explicit provider/model selection | Shared job/reward contract; backend-specific live cell remains open | Not yet—accepted judge calibration and packaged training evidence remain open |

The RC may expose these contracts for qualification. Stable `0.4.0` requires
the open gates above; source registration or a successful unit test alone does
not promote a matrix cell.
