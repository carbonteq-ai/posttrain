# Posttrain v0.3

Posttrain v0.3 provides a complete path from a project-owned training decision
to an immutable job, a managed run, and reviewable qualification evidence. The
series includes three releases:

| Release | Highlights |
| --- | --- |
| [v0.3.0](https://github.com/carbonteq-ai/posttrain/releases/tag/v0.3.0) | Portable projects, provider-free planning, immutable OCI jobs, and durable run control |
| [v0.3.1](https://github.com/carbonteq-ai/posttrain/releases/tag/v0.3.1) | Packaged evaluation environments, run-owned evaluation contracts, Observatory views, and safe purge |
| [v0.3.2](https://github.com/carbonteq-ai/posttrain/releases/tag/v0.3.2) | Gemma 4 support, structured tool rendering, adapter qualification, and paired-assistant MTP |

## Developer features

### Create a portable post-training project

`posttrain init` creates an installable project with an SFT or GRPO starter, a
project-local Python environment, catalog overlays, and work packages. Runtime
state stays outside version control. Projects can add their own models,
datasets, environments, inference profiles, evaluation plans, and execution
targets without modifying the framework catalog.

Machine-specific settings stay outside the project. `posttrain machine`
configures providers, tracking, registries, package indexes, storage, DNS,
trust, credential sources, and registered projects. A project can therefore
move between machines without committing local infrastructure details.

`posttrain catalog list`, `show`, `validate`, and `materialize` make the
combined framework and project catalog visible before a job runs. Optional
catalog-family entry points let a reusable package contribute selections
without coupling the project to a composition host.

### Define reproducible data, workloads, and environments

Projects can use YAML selections or typed Python builders for supervised and
preference datasets. Materialization records the builder, source inputs,
schema, and output digest, and `dataset verify` confirms that a cached result
still matches its manifest.

Serving prompt populations are modeled as workloads rather than training data.
This keeps representative demand separate from project-specific latency and
throughput requirements while still making a benchmark reproducible.

Verifiers environments are independently installable packages. Use
`posttrain environment new` to create one and `posttrain environment add` to
bind an immutable package, taskset, and harness into a project. Local packages
are snapshotted, built as wheels, and verified inside the job image.

### Plan once, then run on local or remote infrastructure

`posttrain job plan` resolves a job without importing its ML backend,
activating an environment, contacting a provider, or publishing an image. The
plan identifies the complete catalog selection and the source, data,
environment, runtime, and execution settings required by the job.

`posttrain job pack` turns that plan into a verified local OCI layout or an
immutable registry image. The package contains the selected project source,
framework wheelhouse, environment wheels, dataset artifacts, catalog closure,
and dependency locks. If an input changes after planning, packing stops instead
of producing a different job under the same identity. `posttrain job diff`
explains why two package identities differ.

The same package can run in a local container or through dstack. Remote runs
support capacity waiting, requested and assigned worker evidence, soft
affinity, bounded log reads, and recovery from an ambiguous submission.

`posttrain runtime images` lists and verifies the release-pinned images used by
each job kind. It can report lock or digest drift, mirror immutable images to a
different registry, and build or publish variants owned by the project.

### Keep jobs moving with continuous reconciliation

`posttrain controller run` is the long-running lifecycle controller for queued
and active jobs. Each reconciliation pass:

- submits queued work when capacity becomes available;
- delivers cancellation requests even when the original client has exited;
- checks the provider and tracking source recorded at submission;
- finalizes terminal evidence and recovery receipts;
- releases settled GPU admissions and advances the queue.

The controller is idempotent, so a process restart can continue from durable
state. `controller run --once` performs one pass for automation or CI, and
`controller status` reports the last health timestamp without changing a run.

For unattended use, run the controller under an external service supervisor.
The v0.3 CLI does not install a daemon, systemd unit, or Ansible role, and it
does not provide `controller enable/disable` commands.

### Operate and retire runs safely

The run CLI exposes provider status and logs, queue and admission state, wait,
cancel, reconciliation, tracking recovery, and cleanup. These operations use
the durable project, provider, and evidence identities captured at submission,
so they continue to work after the submitting shell exits.

Ordinary cleanup preserves evidence. When data must be removed, `run purge`
and `project purge` first produce a reviewable plan across provider resources,
OCI images, tracking runs and artifacts, and local execution state. Applying a
purge requires the plan digest and explicit confirmation. Active runs, unknown
provider state, incomplete lineage, shared artifacts, cross-project consumers,
and unsupported backends block the operation. Progress is journaled so an
interrupted purge can resume without repeating completed actions.

### Train, serve, evaluate, and transform models

The standard job catalog covers the primary post-training workflow:

| Workflow | Job kind | Available path |
| --- | --- | --- |
| Data preparation | `data.prepare` | Supervised and preference datasets |
| Supervised fine-tuning | `train.sft` | TRL, full or LoRA updates |
| Preference optimization | `train.dpo` | TRL |
| GRPO and DAPO | `train.grpo` | TRL or maintained veRL profiles |
| Multi-turn SAMPO | `train.sampo` | TRL or maintained veRL profiles |
| On-policy distillation | `train.distill` | TRL or maintained veRL profiles with fresh Verifiers trajectories |
| Serving | `serve.smoke`, `serve.benchmark` | Managed vLLM or an OpenAI-compatible endpoint |
| Evaluation | `eval.general`, `eval.domain` | Packaged Verifiers environments |
| Quantization | `model.transform` | LLM Compressor AWQ or RTN W4A16/int4-group128 |

Training jobs can retain checkpoints, final adapters or weights, summaries,
native Verifiers traces, and retention manifests. A produced model can be
pinned as an immutable input to a later work package.

Serving benchmarks report time to first token, inter-token latency, throughput,
failure rate, VRAM and KV-cache pressure, and MTP measurements. Capacity sweeps
can identify eligible configurations and Pareto operating points for a
project's workload and constraints.

### Use a broader model catalog

v0.3 includes immutable profiles for the following model families:

| Family | Available v0.3 coverage |
| --- | --- |
| Qwen 3.5 | 0.8B, 2B, and 4B profiles for serving, evaluation, SFT, DPO, online RL, distillation, thinking and tool rendering, and selected native-MTP paths |
| LFM 2.5 | 1.2B Thinking profiles for serving, SFT, DPO, and model rendering |
| Gemma 4 | E2B and E4B serving smokes; 12B Unified serving, LoRA SFT, adapter serving, structured tools, and paired-assistant-MTP GRPO; 31B serving, LoRA SFT, adapter serving, and structured tools |

Gemma 4 profiles use a shared conversation-rendering contract. The qualified
paths are bounded and text-only; they do not establish multimodal training,
full native-context support, or every algorithm for every size.

For rollout acceleration, a model can use either a native MTP head or an
explicitly selected assistant checkpoint. The assistant repository and exact
revision are part of the inference binding and run snapshot. MTP accelerates
generation; it does not change the training objective.

### Evaluate against six published environments

The v0.3 catalog integrates six packages from
`carbonteq-ai/verifiers-environments`. Every package has provider-backed
activation and bounded execution evidence, and every run records the selected
package revision, task population, harness, and native traces.

| Environment | What it measures | v0.3 qualification |
| --- | --- | --- |
| `gsm8k-v1` | Grade-school mathematical reasoning | Bounded live evaluation; also available to online training and distillation |
| `automationbench-v1` | Multi-turn tool use over AutomationBench Simple tasks | Full 200-task evaluation completed: 184 pass, 4 fail, 12 truncations |
| `mmlu-pro-v1` | Five-shot knowledge and reasoning across 14 categories | Bounded live evaluation completed; the full 1,400-task population remains a separate run |
| `ifeval-v1` | Verifiable instruction following and instruction-family facets | Selected 16-task evaluation completed; the full catalog contains 541 tasks |
| `reasoning-gym-v1` | Procedural reasoning across ten deterministic generators | All ten generators exercised; the selected run retained one task error and one truncation |
| `math-python-v1` | Competition mathematics with Python tools and symbolic checking | Live schema-v3 evaluation proved the 500-task plan and compound reporting, but the accepted run was partial |

The general evaluation plan composes MMLU-Pro, IFEval, Reasoning Gym, and Math
Python. A smaller smoke plan covers GSM8K, reverse text, code execution, and
multi-turn alphabet sorting. Evaluations can also target an OpenAI-compatible
policy endpoint while preserving its service and inference identity separately
from locally materialized model variants.

### Read results in Observatory

Evaluation meaning travels with the run. Each evaluation records its effective
population, success predicate, primary reward or metric, native task facets,
compound breakdowns, sampling, and aggregation rules. A later catalog or UI
change cannot silently reinterpret an earlier result.

Observatory provides:

- coverage, configured pass rate, reward, latency, token, and tool-use views;
- reward and verifier distributions, task facets, and compound matrices;
- compatible-run comparison and serving Pareto views;
- tool-aware traces with assistant reasoning, function calls, tool outputs,
  rewards, errors, and truncations;
- lineage across projects, work packages, jobs, runs, models, data, and
  artifacts;
- Python, report export, HTTP, MCP, and frontend access to the same read-only
  evidence model.

Trackio is the default evidence backend, and W&B is available through the same
observation contract. Native Verifiers traces remain the replay source of
truth. Partial traces can appear while an evaluation is running, and missing
signals are never converted to zero or counted as semantic failures.

## Reliability and performance

### Faster rollout and serving paths

Verifiers rollout groups execute concurrently, and concurrent policy requests
are batched before training updates. Distillation aligns teacher log
probabilities with the exact student response tokens and safely ignores masked
padding. Runtime profiles bound batching, compilation, KV-cache use, sleep and
wake behavior, and checkpoint export.

Native and paired-assistant MTP report drafted and accepted tokens, acceptance
rate, KV-cache use, and normalized step measurements. These measurements show
whether speculation improves a serving or rollout profile; they are not used as
model-quality claims.

### Predictable job startup

Environment wheels, activation resources, datasets required by the package,
and backend dependency locks are installed or staged while the image is built.
Workers validate the frozen package and start the job without installing or
upgrading Python packages. Managed inference startup budgets are explicit, so
model and kernel initialization are not mistaken for evaluation timeouts.

### Durable capacity and recovery

Prepared submissions freeze the plan, package, provider, evidence source,
project control location, and binding fingerprint before waiting for capacity.
Local GPU admission is shared across projects; dstack continues to own remote
scheduling. Submission, provider polling, cancellation, reconciliation, and
admission release can all be retried after a crash.

Durable execution records are stored separately from rebuildable caches. Cache
pruning previews recognized cache classes and leaves unknown or durable data
untouched.

### Correct evaluation under partial failure

Reward, configured success, execution errors, truncations, missing signals, and
coverage are separate dimensions. Expected population comes from the frozen
run rather than the number of traces currently visible. Trace synchronization
deduplicates native trace identifiers, tolerates an incomplete final JSONL
line, and retries final ingestion.

Observatory computes rebuildable aggregates from raw traces and run counters.
Bulk reads and atomic source refreshes keep large project views responsive and
preserve the previous readable snapshot if a refresh fails.

### Reproducible release artifacts

The release workflow builds coordinated Python distributions from committed
source, verifies their hashes and first-party pins, installs the candidate in a
clean index-only consumer, checks immutable runtime-image digests, and runs a
packed dstack GPU canary. Final promotion reuses the verified candidate bytes
instead of rebuilding them, and tagging occurs only after publication and
qualification evidence is complete.

## Qualified v0.3.2 Gemma paths

The v0.3.2 qualification packages exercised the supported Gemma paths on real
GPU workers:

- E2B and E4B foundation-serving smokes returned non-empty generation.
- 12B Unified completed bounded LoRA SFT, clean adapter reload, vLLM adapter
  serving, structured tool-call parsing, and a paired-assistant GRPO step with
  two completed rollouts and retained speculative-decoding metrics.
- 31B completed bounded LoRA SFT, clean adapter reload, vLLM adapter serving,
  and a structured OpenAI-compatible tool call.

These are bounded text-only qualifications. They should be used as executable
starting profiles, not as claims of full-context, multimodal, or exhaustive
algorithm support.

## Current support boundaries

- Online training is synchronous. v0.3 does not provide asynchronous learner
  and rollout execution.
- The lifecycle controller is shipped as a long-running command, but service
  installation and host-level restart policy remain operator-owned.
- Standard KV is the qualified default for hybrid Qwen training paths.
  TurboQuant K8V4 long-context use remains experimental.
- Bounded environment qualification confirms package activation and execution;
  it does not imply completion of every full catalog population.
- The Math Python schema-v3 run was accepted with partial progress. v0.3 does
  not claim a completed 500/500 run or independent sandbox isolation for the
  package subprocess path.
